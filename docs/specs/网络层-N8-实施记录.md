### 1.1 一个必须写清的范围澄清

规格 §11 原本写「响应缓存 ❌ 不做」，指的是 **OkHttp 的 HTTP 层 `Cache`**（按 URL 缓存响应）。
后端新增的是 **业务层回传数据缓存**（按 `dataType + userID` 缓存解析后的教务 JSON）。
两者只是同名，完全无关。规格已改：前者仍不做，后者纳入一期；`OkHttpFactory` 仍不装 `Cache`。

## 3 两个关键技术结论

### 3.1 GET 端点是「双 200 形状」，不能套用 §3.2 的常规分流

- 命中：`200` + `{payload, success?, schemaVersion, fetchedAt, stale}`
- 未命中：`200` + `{code:"cache_miss", message, address?}` —— **不是 404**，后端刻意让「没缓存」成为正常流程的一步

⇒ 不能靠 `isSuccessful` 区分，也不能用「非 2xx 解 errorBody」。实现统一声明 `CacheGetResponse`（字段并集），
由 `discriminate()` **只读 `code`** 判别，调用点不各自猜。

### 3.2 `explicitNulls = false` 下显式 `null` 会被解析成 Kotlin `null`（实测）

写测试时发现：`"payload": null` 解出来是 **Kotlin `null`**，不是 `JsonNull`，且与「字段缺失」完全等价。
这正是规格 §3.4 硬规则 2 要的行为。对业务而言两者都表示「没有可用数据」，等价是安全的。
**不要试图区分它们** —— 已写进规格 §3.6 与 `CacheDtoTest` 断言。
