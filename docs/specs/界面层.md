# 界面层规格（一致性与分层约束）

> 本文是 `ui` / `shell` / `design` / `login` / `timetable` 的唯一结构真源。
> 与 `docs/specs/网络层.md §2` 是同一种写法：**目录树 + 分层职责 + 可测性**。
> 改包结构前先读本文；改完更新本文。

## 1 为什么需要这份规格

`net/` 有 `网络层.md §2` 管着，`skin/` 有 ADR-0003~0006 管着，唯独曾经占全部代码
62% 的界面层**没有任何结构约束**，结果长成一个：

- `ui/MainShell.kt` 单文件 1,392 行、单个 Composable 函数 1,129 行、36 个状态、16 个 `LaunchedEffect`；
- 纯数据模型（`CourseEntry`）跑校验要 `require` 依赖 `logic` 的常量；
- 业务数据读写（教师/地点/周次/考勤/备注 + DataStore 防抖落盘）全部堆在导航壳里，0 测试；
- 皮肤数据源 `skin/` 反向 import 表现层的 `ui.theme.NongyuColors`。

**没有 `ui/` 这个中间包了。** 它是「什么都往里放」的温床：顶层包必须是一个

切一刀。新增顶层包需要先写 ADR 说明理由。

## 3 分层职责与可测性（这是分层的全部意义）

| 层 | 职责 | 能在哪测 | 硬约束 |
| --- | --- | --- | --- |
| `*/model/` | 数据结构、不变量 | **纯 JVM** | **禁止** import `android.*` / `androidx.compose.*`，**禁止**依赖本域其他层 |
| `*/logic/` | 纯函数、常量、几何换算 | **纯 JVM** | 同上；只允许依赖 `model/` |
| `*/data/` | 持久化、仓库接缝、网络抓取 | 部分纯 JVM（DataStore 需 Instrumented） | 可依赖 `model/` `logic/` |
| `*/ui/`、`shell/` | Composable | 编译期 + 真机验收 | 只允许依赖本域 `model`/`logic`/`design`，**禁止**直接 import 另一个域的 `ui` |
| `design/` | token、主题、通用零件 | 编译期 | **禁止**依赖任何业务域 |

依赖方向固定为：

```text
model ← logic ← data ← ui
design ← ui（所有 UI 都可以用 design，design 不认识任何业务）
```

### 3.1 `skin` 与 `design` 的依赖是单向的，不要退回去

`skin/` 需要 `NongyuColors` 这个**纯 `@Immutable data class`**（token 定义），
而 `design/Theme.kt` 需要 `SkinSource` / `SkinResolution` 来注入皮肤色板。
两者看起来像倒挂，实际**不构成环**：

```text
skin/  ──> design/NongyuColors.kt     （只用 token 数据结构）
design/Theme.kt ──> skin/SkinSource   （只做注入，唯一一处）
```

`skin/` 里**不得**出现对 `NongyuAppPlusTheme` / `LocalNongyuColors` / `NongyuTheme` /
`uiScaleFor` 的任何引用；`design/` 里除 `Theme.kt` 外**不得**出现任何 `appplus.skin` 引用。
两条都可以用 grep 一条命令核查。

### 3.2 已修正的倒挂（不要退回去）
| 曾经的问题 | 现状 |
| --- | --- |
| `skin/` import `ui.theme.NongyuColors` | 色板迁到 `design/NongyuColors.kt`，`skin` 只依赖 `design` |
| `model/CourseEntry` 的 `require` 依赖 `logic` 常量 | `PERIOD_COUNT` / `TOTAL_WEEKS` 下沉 `model/TimetableLimits.kt` |
| `logic/TimetableAxis`、`TimetableGeometry` 在 KDoc 里链到 `ui/` 的类 | 改成反引号文本，不再产生跨层编译依赖 |
| 屏宽自适应 `411f` + `coerceIn(0.85f, 1.25f)` 在两处各写一遍 | `design/UiScale.kt` 的 `uiScaleFor(widthDp)` |
| 登录会话状态机住在 `ui/login` | `login/session` + `login/model`，`ui` 只剩界面 |

## 4 `MainShell` 的边界（重要）

`MainShell` 允许持有：页面路由（`selectedTab`）、底部条形态与动画、命中层级顺序、
星云球状态、时间条与遮罩的置顶顺序。

`MainShell` **不允许**承担（2026-11-12 已全部外移，不要再写回去）：

- ❌ 业务数据读写的**规则**（教师/地点/周次/考勤/备注该显示什么、该不该落盘）
  → `timetable/logic/CourseDetailRules.kt`，16 条单测；
- ❌ 纯判定逻辑（如「这节课是否已结束」）→ `timetable/logic/PeriodEnded.kt`；
- ❌ 形态推导的 `when` 顺序 → `shell/ShellState.kt` 的 `deriveBarMode`，单测锁定；
- ❌ 底栏高度与三档吸附的算式 → `shell/BarHeight.kt` 的 `barTargetHeight` / `snapDetailStage`；
- ❌ 各形态的**内容** → `shell/bar/` 四个文件；星云球与 dim/雷达波 → `shell/orb/OrbHost.kt`。

`MainShell` 现在只做：「读状态 → 传参 → 调回调」的组合。剩下的约 760 行代码（不含注释）
是路由、命中层级、时间条与三个子窗体的编排，属于壳本身该干的事。

### 4.1 新增一种「底栏变形形态」要动几处（2026-11-12 实测）

**背景**：有多个页面都可能需要「占用底栏位置变形」（像课程详情卡那样）。
2026-11-12 做过一次 spike：给 `BarMode` 加一个 `ExplorationPage` 占位形态，
只做最小编译通过所需的改动，实测记录如下，然后**已回退**（结论留文档，代码不留死形态）。

**实测结果：4 个既有文件 + 1 个新建文件，22 行插入、3 行修改。**

| # | 位置 | 改什么 |
| --- | --- | --- |
| ① | `ShellState.kt` 枚举 | `BarMode` 加一个值 |
| ② | `ShellState.kt` `DismissTarget` | 加一个退出目标 |
| ③ | `ShellState.kt` `dismissTargetOf` | 加一个分支 |
| ④ | `BarHeight.kt` `BarMetrics` | 加一个高度字段 |
| ⑤ | `BarHeight.kt` `barTargetHeight` | 加一个分支 |
| ⑥ | `MainShell.kt` `dismissAction` | 加一个分支（`when (dismissTargetOf(...))`） |
| ⑦ | `MainShell.kt` `barCorner` | 加一个分支 |
| ⑧ | `MainShell.kt` `AnimatedContent` | 加一个内容分支 + import |
| ⑨ | 测试构造点 | `BarMetrics(...)` 所有构造点补参数 |
| ⑩ | 新建 | 该形态的内容 Composable |

**比数字更重要的两个发现：**

1. **编译器是逐个报错、不是一次全报。** 实测经历三轮才收敛：第 1 轮只报 `dismissTargetOf`，
   第 2 轮再报另外 3 处，第 3 轮 `BarMetrics` 新增字段的缺口要等**测试编译**才暴露。
   **不能靠「编译过了」判定改完。**
2. **写了 `else` 的 `when` 会永远静默不报。** 漏改一处不会编译失败，
   只会让该形态在某个维度上行为错误（高度对但圆角不对，或圆角对但点外面不退出），
   只有真机逐形态点一遍才能发现。

**结论：暂不做 `BarSlot` 抽象，触发条件写死如下。**

现状（5 形态 / 4 处改动）仍在可控范围；而 `BarSlot` 要把 `@Composable` lambda 塞进数据结构，
会碰上重组语义的坑（lambda 捕获、`remember` 作用域、`AnimatedContent` targetState 比较），风险不低。

> **触发 `BarSlot` 重构的条件：出现第 3 个「底栏变形页」时。**
> 届时钟形态数达 7～8、改动点开始成为负担，且能拿到 3 个真实需求来验证抽象是否合理。
> 在那之前，新增形态按上表逐项改，**并配该形态的单测**（`ShellState` / `BarHeight` 各一条），
> 用测试代替编译器兜住漏改。

### 4.2 命中层级：改之前先看这张表

`MainShell` 里点击能否落到正确目标，靠的是 **Compose「后声明的先命中」**。
三张卡片（课程详情 / 日程明细 / 添加日程）的「点卡片外退出」层必须是**全屏 + 声明在底栏之前**：

```text
[后声明 = 先命中]
  输入栏 / 底部条（卡片本体住在这里，且更靠后）
  ...
  全屏 dismiss 层（点这里 = 点卡片外 = 退出）
[先声明 = 后命中]
```

历史上错两次：放在整屏最顶会连卡片内部一起吃掉；干脆不放则卡片外点了没反应。
另外，**详情卡还挂过一层「消费点击」的 clickable**，它吃掉了横杠的 pointerInput，
导致第二次上划（进第四态）手势完全收不到 —— 现已删除，不要再加回来。

**重构这段顺序时，必须真机验证「点课程盒子外部退出、点卡片内部不退出」。**

## 7 本轮解耦的约定（后续改动请沿用）

1. **界面层不持有业务规则**。凡是「什么情况下该写、该显示什么值、该不该落盘」这类判定，
   一律下沉 `logic/` 并配单测；Composable 只做「读状态 → 调回调」。
2. **state 仍留在 Shell**，只把「内容」和「规则」挪出去。这样命中层级与动画时序不受影响，
   是这四步能全程零回归的原因。
3. 抽内容时**只传它真正需要的参数**，不要整包传 Shell 的状态对象 —— 否则等于把耦合藏进了参数表。
4. 每个文件的 KDoc 顶部写明「从 MainShell 原样搬出，行为未改」以及该块**实测踩过的坑**，
   这些坑是最难重建的知识。

## 8 事故档案（从 `MainShell` 注释迁入，2026-11-12）

> 这一节收纳原先散在 `MainShell.kt` 里的 149 行「为什么不能这么写」注释。
> 代码里只保留一行指向对应条目的指引。**改动相关代码前先读对应条目。**

### §8.1 层级与命中测试

**A. `dim` 必须画在底栏之前。**
历史上它画在底栏之后（为了「把导航栏一起压暗」），那时输入框是浮在 `dim` 之上的独立控件，
所以没问题。现在输入态与详情态都住进底栏本体，若仍画在底栏之后，整块底栏会被这层
近乎不透明的遮罩完全盖住 —— 表现是「点星云球后什么都没出现」（实测整片深灰）。
输入态的压暗层同样画在底栏**之前**，于是它压暗课表、不压底栏。
长按那层（`dimAlpha`）画在底栏之后、会把底栏一起压暗，两者互不干扰。

**B. 卡片外退出层必须是「全屏 + 声明在底栏之前」。**
维护者 2026-11-11 拍板：课程卡 / 日程卡 / 添加日程三者统一 ——
点「卡片之外」退出、点「卡片之内」不退出。

实现依赖 Compose「后声明的先命中」：这层全屏但声明在底栏之前，而卡片本体住在底栏里，所以

- 落在卡片上的点击 → 底栏先命中 → 这层收不到 → 卡片内部不退出 ✅
- 落在其余区域 → 只有这层能接 → 退出 ✅

**前两版都不对**：放整屏最顶（底栏之后）会连卡片内部一起吃掉；干脆不放则卡片外无处接收点击
（点了没反应）。

**C. 底栏容器必须自己「消费点击」。**
卡片形态下容器就是卡片本体，落在它上面的点击必须停在这里，不能穿透到卡片外退出层，
否则点卡片内部也会退出。放在容器上而不是各卡片内容里，是因为卡片内容高度随形态变化，
**内容之外的容器留白同样是「卡片内部」**，也得消费掉。
横杠等子控件的 `pointerInput` 在更内层，命中测试先给子节点，拖拽不受影响。

> ⚠️ 但**详情卡内部**不要再挂一层消费点击的 `clickable` —— 见 §8.3 D。

**D. 星云球只在常态接收触摸。**
球浮在内容之上，它的手势区会盖在课表底部，否则在课程卡片上点按/长按会被判成星云球的操作
（维护者反馈）。输入态/详情态时球本来就在溶解，也不需要交互。

### §8.2 底栏高度与动画

**A. 必须用显式 `Animatable`，不能用 `animateDpAsState`。**
后者每帧读一次 `animationSpec`：拖拽期用 `tween(0)` 跟手，松手那帧若 spec 仍是 0 就会瞬间跳变，
表现为「上划/下降没有动画」。显式 `Animatable` 把两条路径分开：
拖拽中 `snapTo`（零延迟纯跟手）、吸附/打开/退出收拢 `animateTo(spring)`（有弹性过渡），
互不吞掉。

**B. `LaunchedEffect` 的 key 必须包含 `detailStage`，且只包含真正的输入。**
上划吸附到 `Full` 时 `barMode` 仍是 `Detail`、`isCollapsing` 仍是 `false`，若只盯这两个 key
effect 不会重跑，高度就停在简介态 —— 这是「上划/下降没有动画」的另一半根因。
反过来，旧 key 里还有 `addingSchedule`、`scheduleDetailId`，但这两者信息已由 `barMode` 承载
（见 `deriveBarMode`），属冗余 key，会让同一变化触发多条重跑路径。现固定为 4 个。

**C. 形态进度要在 `brief → full` 这段归一化。**
用 `navHeight` 做分母会让简介态就有约 0.24 的进度，导致胶囊半透明、K-V 提前浮现（两形态糊在一起）。

**D. 拖到底不能立刻清 `detailCourse`。**
那样 `AnimatedContent` 当帧就把内容换成导航栏、收拢动画根本来不及跑。只置 `isCollapsing`，
由高度动画跑完后再统一清。

### §8.3 星云球

**A. 不能 `clip(CircleShape)`。**
星云球边缘在渲染层已羽化到透明，硬裁剪会把软边切成 3D 球的硬圆轮廓。

**B. 溶解/汇聚用 `Animatable` 区分正反两个时长。**
导航栏进入变形（Input/Detail）时球**溶解**（粒子外散 + 渐隐，280ms）；回到常态**汇聚**
（从四周收拢回球心，420ms）。溶解略快、汇聚略慢，收拢感更自然。

**C. 雷达波方向语义。**
进入激活态（变黑）从球心**向外扩散**并淡出；退出激活态（变亮）从外侧**向内回收**到球体
（呼应「能量收回」，不是再释放一次）。`pulseKey` 自增重跑动画，`pulseExpand` 标记本轮方向。

**D. 详情卡上不能挂「消费点击」的 `clickable`。**
当初是为防点详情卡穿透到收起层，但收起层现在放在课表**之下**（白名单分层方案），
与底栏里的详情卡不在同一命中链上，这层已多余。**而且它会吃掉横杠的 `pointerInput`，
导致第二次上划（进第四态）手势完全收不到**（实测日志无 end 回调）。

**E. `dim` 只在长按态出现，且只保留一层。**
输入态不再整屏压暗：输入栏本身就在底栏里，整屏压暗会把输入栏一起压灰
（历史上输入栏浮在上层所以没暴露）。输入态需要的是「底栏可见 + 背后课表变暗」，
由单独的 `inputScrim` 负责。曾经在底栏内部用 `drawWithContent` 又补过一层 `longPressDim`，
两层叠加导致过暗，已删除。

### §8.4 底栏容器样式

**A. 不能用 `.alpha(navAlpha)` 作用于整个容器。**
`navAlpha` 的语义是「导航项该不该显示」，作用在容器上会把输入态/详情态的内容一起干掉。
历史上输入框浮在这层之外所以没暴露，住进容器后立刻被隐藏。
正确做法：容器始终不透明，只让导航项自己淡出。

**B. 底栏占位上报的是「底栏自身高度」，不是「顶边 y 坐标」。**
曾用 `positionInRoot` / `boundsInRoot` 取顶边再做坐标换算，**两次都出现了偏差**
（一次少让出、一次多让出），因为 padding 与子树坐标叠加后极易算错、不同机型表现不一致。
改为直接上报底栏自身高度，它就是「内容区底部必须让出的像素数」，无需任何转换。

**C. 占位高度只在「常态 + 高度动画已稳定」时上报，两个条件缺一不可。**
1. `barMode == Normal`：点开详情卡（62→128dp）时不该推动课表（弹出版挤压）。
2. `barHeight == navHeight`：退出详情卡时 `barMode` **立刻**回到 Normal，但 `barHeight`
   还在 128→62dp 的动画途中。此时无条件上报会逐帧把中间高度传给课表，整张课表一帧帧改大小
   —— 就是「退回时瞬间变大小、弹一下」。

### §8.5 状态与副作用

**A. 备注不能用 `collectAsState` 直接喂 `TextField`。**
那样每次输入都要等 DataStore 回读，写入与回读互相打架（**实测重启后丢值**）。
正确做法：本地 `mutableState` 做 UI 真源，打开卡片时读一次，之后每次改动既更新本地、又异步落盘；
能否落盘的判据见 `timetable/logic/CourseDetailRules.kt`。

**B. 时间文字的清除 effect，key 只盯 `rulerDragging`。**
曾同时盯 `rulerFocus` 和 `rulerDragging`，两者在 `onDragEnd` 里连续写，可能出现
「focus 已 null 但 dragging 仍 true」的一帧，导致清除分支不触发，时间文字一直挂在屏幕上。

**C. 图标线宽只读取已解析好的皮肤结果，不要在这里再 `resolve()`。**
启动路径上的解析只在 `MainActivity.setContent` 之前做一次（ADR-0006）。
曾在此处再 resolve 一次，导致冷启动多做一遍磁盘读 + 一遍日志。

**D. 课时内容的位置必须用 `TimetableGrid` 上报的实测值。**
手算公式**已连续错两次**（漏底栏占位、漏工具条预留），而这段区域还受状态栏、表头、
各种 padding 影响，永远算不全。实测值天然包含所有偏移，只需做一次 dp 换算。

### §8.6 尺寸自适应

**A. `uiScale` 基准是 411dp，上限 1.25。**
固定 dp 在不同 dp 宽度的设备上观感差异极大（蓝叠 1920x1080@240dpi = 1280dp 宽，
手机 1080x2400@420dpi ≈ 411dp 宽）。上限曾放到 1.55，实测在大画布上整套 UI 被等比放大得
过于笨重，现压到 1.25。**改动基准只需改 `design/UiScale.kt`**。

**B. 球体也必须参与缩放。**
否则其他元素变大、球固定不动会显得变小。球径演进：120dp →（导航栏 74→62dp 后）→ 96dp
→ 78dp（光晕外扩使观感大于几何尺寸）。
