# 网络层规格（一期）

> 本文件是 **农屿 App 翻新版 · 网络层** 的可开工规格，由地图 [#41](https://github.com/NongyuSystem/nongyu-app-plus/issues/41) 的 11 张决议票与 4 篇调研合拢而成（合拢票 [#56](https://github.com/NongyuSystem/nongyu-app-plus/issues/56)）。
>
> **它写给谁**：没有参与过本图讨论的实现者。读完这一份就能开工，不需要再翻回原票。
>
> **它不做什么**：不写生产代码、不加依赖、不改构建文件。代码片段只是**形状**（签名与结构），不是实现。
>
> **状态**：一期 = 「可调用的门面 + 可测的纯逻辑」，**不接 UI、不做登录**。一期网络层没有任何 UI 调用方，这是刻意的（#50 Q6）。

## 0 先说清楚：一期能做什么、不能做什么

这一段是全篇最容易被忽略、但最影响排期的部分。**网络层建好 ≠ 能联调业务**。

| 能力 | 一期状态 | 一句话依据 |
| --- | --- | --- |
| 传输层（Retrofit + OkHttp） | ✅ 已落地并构建通过 | #48 实测 debug/release 双通过 |
| JSON 解析 | ✅ kotlinx.serialization 1.10.0 | #45 决议，插件生效有字节码证据 |
| 契约映射（16 条路由 → 3 个 interface） | ✅ 只定义，**只构造 identity 公开端点** | #52 / #50 Q2 |
| 鉴权接缝 | ✅ 接口 + 固定注入值 | #43 Q1=D / Q5=A |
| 登录 | ❌ **不做**，且后端 `/identity/login` 现在返回 401 | #46 §4.4 / #52 Q2=B |
| 业务端点（课表、帖子、教务托管…） | ❌ **仍全缺**（后端这一批未做） | #46 §7；本轮只新增回传缓存子域 |
| **回传缓存端点**（`/school/cache/:dataType` 3 条） | ✅ **纳入一期**（本轮变更，见 §3.6） | 后端 `jiaowu.RegisterCache`；独立 `CacheApi`，payload 原始 JSON 透传 |
| 证书固定 | ❌ 有意推迟（无生产域名） | #49 Q2=A |
| 响应缓存（**OkHttp `Cache`，HTTP 层**） | ❌ 不做 | #47 Q4=A。⚠️ 与上一行的「业务层回传缓存」是两件事，不要混淆 |
| 被 UI 调用 | ❌ 不允许（无 ViewModel） | #50 Q6；接入 cache 端点不等于接 UI |

**一期实际能打出去的端点**（详见 §9 第 4 对交叉核对）：

- `GET /healthz` —— 公开，降级装配下可用（已实机确认）。
- `POST /identity/mailcode/send` —— 公开，可用。
- `POST /identity/login/admin` —— 公开路径，**但成功路径需要 `DATABASE_URL`**，降级装配下走不通。
- `GET/POST/DELETE /school/*`（6 条）与 `GET/POST /school/presence`（2 条）—— 需要 Bearer；用**降级装配下自签的 token** 可通（#46 实机确认 `/school/address` 返回 200）。

⇒ 门面（`NongyuApi`）一期只暴露 3 个方法：`healthz()` / `sendMailCode()` / `loginAdmin()`。`SchoolApi` 与 `PresenceApi` **只写 interface，不构造实例**。

## 1 依赖与版本钉法

### 1.1 已经落地的（#48 实测通过，改动仍在工作区，未提交）

当前工作区（分支 `feat/skin-decoupling-and-perf`）已包含以下改动，**不要再加一遍**：

| 坐标 | 版本 | 位置 |
| --- | --- | --- |
| `com.squareup.retrofit2:retrofit` | **3.0.0** | `app/build.gradle.kts` → `implementation` |
| `com.squareup.okhttp3:okhttp` | **4.12.1** | 同上（显式覆盖 Retrofit POM 自带的 4.12.0） |
| `com.squareup.retrofit2:converter-kotlinx-serialization` | 3.0.0 | 同上 |
| `org.jetbrains.kotlinx:kotlinx-serialization-json` | **1.10.0** | 同上 |
| `org.jetbrains.kotlinx:kotlinx-coroutines-core` / `-android` | **1.9.0** | 同上 |
| `libs.plugins.kotlin.serialization` | 2.3.0 | `plugins {}` 里 `alias(...)` |
| `<uses-permission android:name="android.permission.INTERNET" />` | — | `app/src/main/AndroidManifest.xml` |

版本为什么钉这几个（每条都有实测依据，别改）：

- **OkHttp 必须显式钉 4.12.1**：Retrofit 3.0.0 的 POM 自带 `okhttp:4.12.0`，不钉就会解析到 4.12.0（#48 用依赖树 `okhttp:4.12.0 -> 4.12.1` 证明钉子生效）。**不能升到 5.x**：`okhttp-android` 5.5.x 要求 `compileSdk 37`，本机 SDK 只到 36。
- **`kotlinx-serialization-json` 必须钉 1.10.0**：与 Kotlin 2.3.0 完全同源（mv 2.3.0 + stdlib 2.3.0）。1.11.0/1.12.0 能编过，但 **1.12.0 要求 stdlib 2.4.10，会抬版本**，所以不用。
- **coroutines 必须显式声明**：改动前全工程一处 `coroutines` 都没有，靠 `androidx.lifecycle:lifecycle-common:2.10.0` 传递进来。实测本工程**本来就解析到 1.9.0**，钉死等于把既有事实写进版本目录（零抬升、零体积增量）。不钉的后果：将来 Compose/lifecycle 升级会把版本悄悄抬走。
- **serialization 插件不需要 `buildscript { classpath(KGP) }`**：AGP 9 内置 Kotlin 下按版本目录 `[plugins]` 一行 + 模块 `alias(...)` 即可。`$$serializer` 生成在 `intermediates/built_in_kotlinc/` 下 —— 这个目录名证明走的是内置 Kotlin 路径（#48 实证 + #42 的 AGP 字节码证据）。
- **`INTERNET` 必须手写**：retrofit / okhttp 是 AAR-free jar，**不携带 manifest**，只声明依赖时合并清单里没有该权限（#48 用 `aapt2 dump permissions` 实证）。漏了就是运行时 `UnknownHostException` / `SecurityException`。代价 +32 B。

## 2 包结构与分层

### 2.1 目录树

包名根 `com.nongyu.appplus`，网络层全在 `net/` 下。这套拆分**照抄 `skin/` 的既有范式**（`ColorPayloadParser` 纯逻辑 + `ColorPayloadJson` 薄适配）：本工程只有一个主接缝可测，网络层必须保持同一形状。

```text
app/src/main/java/com/nongyu/appplus/net/
├── core/                        纯逻辑层（零 Android 依赖，纯 JVM 可测）
│   ├── ApiFailure.kt            # §5.1 的 sealed class 六类
│   ├── ApiErrorCode.kt          # §3.3 的 23 个字符串常量 + Unknown 兜底
│   ├── RetryPolicy.kt           # §5.3 的重试判定纯函数
│   ├── SessionInvalidRules.kt   # §4.3 的「域 + code + HTTP 状态」判据
│   ├── UrlBuilder.kt            # base URL 规范化与校验
│   └── ApiCall.kt               # 统一包装：catch 顺序 + 重试执行 + Response/errorBody 拆解
├── http/                        Android 薄壳（但全部可在纯 JVM 测）
│   ├── OkHttpFactory.kt         # 超时 / retryOnConnectionFailure / 拦截器装配
│   ├── AuthInterceptor.kt       # 调 AuthTokenProvider；无 token 时按分区短路
│   ├── SafeLoggingInterceptor.kt# §6.3 脱敏 + 日志（**一个拦截器，不是两个**）
│   └── SessionInvalidInterceptor.kt # 读响应，按判据回调
├── api/                         Retrofit interfaces（三域拆）
│   ├── IdentityApi.kt
│   ├── SchoolApi.kt
│   └── PresenceApi.kt
├── model/                       DTO（全可空，照抄 camelCase）
│   ├── IdentityDto.kt
│   ├── SchoolDto.kt
│   ├── PresenceDto.kt
│   └── ApiErrorDto.kt
├── auth/
│   ├── AuthTokenProvider.kt     # fun interface，N1 声明
│   ├── SessionInvalidListener.kt# fun interface，N1 声明
│   ├── SessionStore.kt          # interface，N1 声明
│   ├── MinimalSessionStore.kt   # security-crypto 实现（N5）
│   └── DefaultSessionInvalidListener.kt # 调 clear() 的默认实现（N5）
├── NetConfig.kt                 # BASE_URL —— **同名文件放 debug / release 两个源集**（§2.3）

### 2.2 分层职责与可测性（这是分层的全部意义）

| 层 | 职责 | 能在哪测 | 为什么 |
| --- | --- | --- | --- |
| `core/` | 失败分类、重试判定、失效判据、URL 拼装、调用包装 | **纯 JVM**（`:app:testDebugUnitTest`） | 零 Android API；这是唯一能覆盖「决策逻辑」的地方 |
| `model/` | `@Serializable data class` 的序列化/反序列化 | **纯 JVM** | serialization 实测可在纯 JVM 跑通（#48）。这是选它而不是 `org.json` 的决定性理由 |
| `http/` | OkHttp 装配与拦截器 | **纯 JVM + MockWebServer** | OkHttp 本身是 jar，能在 JVM 跑 |
| `auth/` | 会话存储（Keystore） | **只能 Android 运行时** → 蓝叠手测 | Keystore 在纯 JVM 不存在 |
| `NongyuApi` + `api/` | 端到端（interface ↔ 真实 JSON 形状） | **纯 JVM + MockWebServer + fixture** | |

### 2.3 源集分流：`NetConfig` 与 `DefaultTokenProvider` 必须是两份

**这是一个必须在实现前就定下来的结构性约束，否则 release 变体编译不过。**

`buildConfigField` 只在 `debug {}` 里声明时，**release 变体不存在 `BuildConfig.DEV_TOKEN` 字段** —— 这不是「运行时为空」，是「编译期没有这个符号」。任何在 `src/main/java` 里引用它的代码都会让 `assembleRelease` 直接失败。

同时 #43 Q5=A 要求「结构性保证 DEV_TOKEN 不进 release 包」，明确否掉了运行时 `if (BuildConfig.DEBUG)`。

**两条要求交集只有一个解：按源集放同名文件。**

```text
app/src/main/java/com/nongyu/appplus/net/NetConfig.kt          ← 不放，用下面两个
app/src/debug/java/com/nongyu/appplus/net/NetConfig.kt
    object NetConfig { const val BASE_URL = "http://127.0.0.1:3000/" }
app/src/release/java/com/nongyu/appplus/net/NetConfig.kt
    object NetConfig { const val BASE_URL = "" }   // 生产域名尚不存在（#49 Q2）

app/src/debug/java/com/nongyu/appplus/net/DefaultTokenProvider.kt
    internal fun defaultTokenProvider(): AuthTokenProvider =
        AuthTokenProvider { BuildConfig.DEV_TOKEN }      // 只有 debug 源集能看见
app/src/release/java/com/nongyu/appplus/net/DefaultTokenProvider.kt
    internal fun defaultTokenProvider(): AuthTokenProvider = AuthTokenProvider { null }
```

`BASE_URL` 的两种可行放置方式，**本规格选后者**：

| 方式 | 做法 | 取舍 |
| --- | --- | --- |
| A（否） | 全在 `buildConfigField`，`defaultConfig` 给空串、`debug {}` 覆盖 | release 里字段存在但为空，不是结构性隔离 |
| **B（本规格）** | `NetConfig` 按源集两写，`buildConfigField` 只服务 `DEV_TOKEN` | 真正结构性；代价是多两个小文件 |

契约：**`BASE_URL` 必须在 host 之后以 `/` 结尾**（Retrofit 的 `baseUrl()` 要求）。`UrlBuilder.normalize()` 负责校验并在缺失时补 `/`，`BASE_URL` 为空串时**在 `NetHolder` 首次构造处抛带明确文案的异常**（`"release 变体未配置 BASE_URL"`），不要让它变成一个静默的坏 URL。

### 2.4 装配：惰性 holder，绝不在启动路径构造

```kotlin
object NetHolder {
    val api: NongyuApi by lazy { buildNongyuApi() }   // 没人调用就不构造
}
```

**为什么必须惰性**：`docs/adr/0006-冷启动只读本地皮肤包不碰网络.md` 明写「冷启动只读本地、绝不碰网络」。当前启动路径是 `MainActivity.onCreate` → `enableEdgeToEdge()` → `FileSkinSource.resolve()`（同步读本地磁盘）→ `setContent { ... }`，没有任何网络入口。

被否掉的：`Application.onCreate` 构造（违反 ADR-0006，还要新建一个 `Application` 类扩大改动面）；每次调用构造（丢掉 OkHttp 连接池，且每次重建 Keystore 读）。

**三条守卫（写进代码注释，别只写在文档里）**：

1. **禁止在 Composable / Activity / `onCreate` 路径上访问 `NetHolder`**。一期网络层不接 UI（#50 Q6）。
2. `by lazy` 默认是 `SYNCHRONIZED` 模式 —— 首次访问会阻塞调用线程。它不做网络 IO（只构造 OkHttpClient / Retrofit），但**会话存储的 Keystore 初始化是磁盘 + IPC 的**，所以 `MinimalSessionStore` 自己必须也是惰性打开（构造时只存 context，首次 `currentToken()`/`clear()` 才 `create()`）。
3. 将来接入「启动时恢复会话」或「皮肤包下载器」（#53）时，**必须在首帧之后**。ADR-0006 的约束是对整条启动路径的，不只是皮肤。

## 3 契约映射

### 3.1 路由表 → interface（16 条）

后端 `apps/nongyu-backend-plus` **没有 `/api` 前缀**，路径以 `/identity/`、`/school/`、`/healthz` 开头。Retrofit 的 `@GET`/`@POST` **不写前导斜杠**（`@GET("identity/me")`），保留 base URL 路径可替换性。

| # | method | path | interface 方法 | 一期构造 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 1 | GET | `/healthz` | `IdentityApi.healthz(): Response<HealthzDto>` | ✅ | 公开；**有 JSON body**（`{"status":"ok"}`），不要用 `Response<Unit>` |
| 2 | GET | `/school/address` | `SchoolApi.address(@Query("target") target: String?, @Query("path") path: String?)` | ❌ | query 是本仓唯一带 query 的端点 |
| 3 | GET | `/school/fetch` | `SchoolApi.fetch(...): Response<ResponseBody>` | ❌ | **`application/octet-stream`，不是 JSON**；走 `ResponseBody` + `@Streaming` |
| 4 | GET | `/school/captcha` | `SchoolApi.captcha(): Response<CaptchaDto>` | ❌ | |
| 5 | POST | `/school/login` | `SchoolApi.login(@Body ...): Response<SchoolLoginDto>` | ❌ | `expiresAt` 是 **RFC3339 字符串**（见 3.4） |
| 6 | DELETE | `/school/logout` | `SchoolApi.logout(): Response<LogoutAckDto>` | ❌ | 返回 `{"status":"ok"}` |
| 7 | POST | `/school/login/accel` | `SchoolApi.loginAccel(@Body ...): Response<AccelDto>` | ❌ | |
| 8 | POST | `/school/presence` | `PresenceApi.report(@Body ...): Response<PresenceReportDto>` | ❌ | 响应键是 `userID`（大写 ID） |
| 9 | GET | `/school/presence` | `PresenceApi.decide(): Response<PresenceDecideDto>` | ❌ | |
| 10 | POST | `/identity/login` | `IdentityApi.login(@Body ...)` | ❌ | **后端缺陷：可吊销装配下恒 401**（#46 §4.4），不纳入一期 |
| 11 | POST | `/identity/login/admin` | `IdentityApi.loginAdmin(@Body ...): Response<LoginDto>` | ✅ | 公开路径；成功路径需 DB |
| 12 | POST | `/identity/logout` | `IdentityApi.logout(): Response<LogoutAckDto>` | ❌ | 需 Bearer + `CtxSessionID` |
| 13 | POST | `/identity/mailcode/send` | `IdentityApi.sendMailCode(@Body ...): Response<MailCodeAckDto>` | ✅ | 公开 |
| 14 | GET | `/identity/me` | `IdentityApi.me(): Response<ProfileDto>` | ❌ | **无 DB 时后端根本不注册该路由** → 404 文本 |
| 15 | PATCH | `/identity/me/profile` | `IdentityApi.updateProfile(@Body ...): Response<ProfileDto>` | ❌ | 同 14 |
| 16 | GET | `/identity/users/:studentNo` | `IdentityApi.user(@Path("studentNo") ...)` | ❌ | 后端注释称「需管理员」但无角色校验，属后端缺陷 |

**按域拆三个 interface**（不做单个大接口）：与 §4.3「按前缀判失效」同源；且 `school` 域那 5 条必然等「客户端直连学校」的 future 票，混在一起会拖累 identity 域。

> 精度提醒：`@GET("identity/me")` 不带前导 `/`。带前导斜杠会解析到 host 根、丢掉 baseUrl 的 path 部分。当前 baseUrl 无 path，两种写法等价，但**规则只留一种**。

### 3.2 双形状处理：`Response<T>` + 手工解析 `errorBody`

同一个端点有两条完全不同的响应形状：**成功是裸业务结构体（无信封）**，**失败是 `{"code":"..."}` 或 `{"code":"...","message":"..."}`**。

- 端点一律声明为 **`suspend fun x(...): Response<T>`**。
- 成功（2xx）：取 `body()`。
- 失败（非 2xx）：手工读 `errorBody()`，解析成 `ApiErrorDto`（`code` / `message` 都可空）。
- **每个调用点的 `if (!isSuccessful)` 都集中在 `net/core/ApiCall.kt` 这一个包装里**，不散落到业务代码 —— 这正是 #52 Q3 说的「错误分类的集中点」。

被否掉的：

| 备选 | 否掉的理由 |
| --- | --- |
| `ApiResult<T>` 自动拆包 | Retrofit 只能声明一种返回形状，做不到 |
| `suspend fun x(): T` + 捕 `HttpException` | `errorBody` 会被消费两次，OkHttp 上易踩 "response body already consumed" |
| 用 `@JvmSuppressWildcards` 之类机制区分双形状 | 那是给泛型签名补注解，与响应形状无关，解决不了这个 |

**两条硬规则**：

1. **errorBody 不是 JSON ≠ `Parse`**。后端未匹配路径返回 `Content-Type: text/plain` 的 `404 page not found`（gin 默认）。这种情况是 `ApiFailure.Http(404, code = null, message = null)`，**不是** `Parse`。规则：**非 2xx 永远归 `Http`/`Business`；`Parse` 只用于「2xx 但 body 反序列化失败」**。
2. **`ApiFailure.Business` 在一期没有产出点**。backend-plus 的错误一律配 4xx/5xx，不存在「200 但 body 是 code」的情况（#46 全范围确认）。保留这个类型是因为契约可能变成 node 风格（200+code），但**实现时不得为它编造分支**；测试用手工构造的 `200 + {"code":...}` 响应覆盖判定规则即可。

### 3.4 DTO 规则

四条硬规则：

1. **全部字段可空**，`= null` 默认值。
2. **客户端不区分「缺字段」与「显式 null」**，二者一律等价为 `null`。后端不得依赖客户端区分这两种形态。（Go 的 `omitempty` / 显式 null / 零值 `""` `0` 在 Kotlin 侧统一成可空类型。零值 `""`/`0` 与缺失的区分由**调用方**按业务判断，DTO 层不做。）
3. **字段名照抄后端 camelCase**（`studentNo`、`className`、`avatarUrl`），**不加 `@SerialName`**。Go 的 JSON tag 已是 camelCase，转一道只增出错面。将来后端真用 snake 时再加。
4. **`Json` 配置固定为** `ignoreUnknownKeys = true` + `explicitNulls = false`。前者让后端加字段不炸客户端，后者的意义见下。

**一期 DTO 清单**（字段全部可空）：

| --- | --- | --- |
| `HealthzDto` | `status` | `/healthz` |
| `MailCodeAckDto` | `sent` | `/identity/mailcode/send` |
| `LogoutAckDto` | `ok`（identity）/ `status`（school） | `/identity/logout`、`/school/logout` **键名不同，不要复用同一个 DTO** |

### 3.5 与 node-server 的差异：只记录，不抽层

维护者已定 Q2=B —— **一期只对 backend-plus，不抽可替换层**。所以 RN 版那些 `/api/app/*` 端点在这里**是「不存在」，不是「留占位」**。

规格里保留一张对照表（放实现时的 KDoc 注释里就够，不必再抄全文）：信封（无/有）、`code` 类型（string/number）、路径前缀（无/`/api/app`）、错误码集合（20 字符串/30 数字，零交集）、令牌格式（2 段 base64url / 3 段 JWT）。**给实现者的唯一指令**：不要试图「兼容两套」，那不是本期的目标，也不是维护者要的。

### 3.6 回传缓存端点（本轮新增，2026-11-11）

后端 `apps/nongyu-backend-plus` 新增 `jiaowu.RegisterCache`，挂 3 条路由：

| method | path | 成功形状 | 备注 |
| --- | --- | --- | --- |
| GET | `/school/cache/:dataType` | `CacheEnvelope` 或 `CacheMissDto` | **同一个端点有两条不同的 200 形状**，见下 |
| POST | `/school/cache/:dataType` | `CacheEnvelope` | 回传解析后的 JSON，体上限 1 MiB（后端校验） |
| DELETE | `/school/cache/:dataType` | `{"invalidated":true}` | 60 秒失效间隔 |

#### 为什么 GET 有两条 200 形状（与 §3.2 不同，不要套用）

- **命中**：`200` + `cacheEnvelope` = `{payload, success?, schemaVersion, fetchedAt, stale}`
- **未命中**：`200` + `cacheMissResponse` = `{code:"cache_miss", message, address?}`（**不是 404**，后端刻意为之，让「没缓存」成为正常流程的一步）

⇒ **不能靠 `isSuccessful` 区分**，也不能套用 §3.2 的「2xx 取 body / 非 2xx 解 errorBody」。实现必须**先看 body 里有没有 `code`**：有 `code` 就是 miss/错误路径，没有才是命中。这一条落在 `CacheApi` 的返回类型上（见下），不要散落到调用点。

#### payload：原始 JSON 透传（维护者本轮拍板 A）

后端 `payload` 是 `json.RawMessage`，**原样透出缓存里存的那段 JSON**。15 类的顶层形状分三种（8 数组 / 3 单对象 / 4 包装对象），且 `RankItem` 等单对象**可为 `null`**。

- 客户端**不解析** payload 内部字段，用 `JsonElement`（`kotlinx.serialization.json.JsonElement`）承接，可空。
- 理由：与后端「原样透出」一致；教务页改字段时客户端不会炸。若将来某类需要结构化，再单独加一个 typed DTO，不动这层。
- ⚠️ `JsonElement` 字段**不能写成 `String`** —— 后端给的是 JSON 值（对象/数组/null），不是被字符串化的 JSON 文本。
- **实测语义（2026-11-11）**：在 `explicitNulls = false` 下，显式 `"payload": null` 会被解析成 **Kotlin `null`**，与「字段缺失」完全等价（不是 `JsonNull`）。这符合 §3.4 硬规则 2。对业务而言两者都表示「没有可用数据」，等价是安全的，**不要试图区分它们**。已在 `CacheDtoTest` 钉住。

#### dataType 受控词表

后端 `ParseDataType` 只认 15 个名字，未知名一律 400 `target_denied`。客户端同样在 `net/model/CacheDataType.kt` 定义这 15 个常量作为**受控词表**，调用方必须传枚举/常量，不许拼裸字符串：

```
course, score, exam, progress, rank, plan, personal, notice, teachingNotice,
competition, classroomInfo, teacherInfo, teacherCourse, classroomCourse, kaike
```

#### 错误码（本子域新增，补进 `ApiErrorCode`）

| code | HTTP | 语义 |
| --- | --- | --- |
| `cache_miss` | **200** | 未命中。`address` 顺带给编码地址，客户端可直接去取数 |
| `schema_rejected` | 400 | 回传体形状校验未通过 |
| `payload_too_large` | 413 | 回传体超 1 MiB（**后端校验，客户端不重复校**） |
| `refresh_too_soon` | 429 | 失效过频，响应头带 `Retry-After` |
| `cache_unavailable` | 503 | 缓存层未配置（未配 Redis/Store） |
| `target_denied` | 400 | dataType 不在词表（已有常量） |

#### 门面形态（维护者本轮拍板：独立 `CacheApi`）

- 新建 `net/api/CacheApi.kt`（3 条路由），**不并入 `NongyuApi`**。
- `NongyuApi` 保持「身份域公开端点」的窄职责；回传缓存走独立入口，等将来接 UI 时由 ViewModel 自行选用。
- 理由：两者鉴权口径、失败形状（双 200）、数据用途都不同，塞进同一门面会让 `NongyuApi` 变成垃圾桶。
- **一期仍不构造 `SchoolApi` / `PresenceApi` 实例**，`CacheApi` 的装配单独放 `CacheHolder`（或由 `NetHolder` 暴露一个 `cache()` 方法），不与 `NongyuApi` 的构造耦合。

#### 与「响应缓存不做」的区分（写死，防误读）

- ❌ **OkHttp `Cache`（HTTP 层，按 URL 缓存响应）** —— 一期不做（#47 Q4=A）。
- ✅ **业务层回传数据缓存（本端点，按 dataType + userID 缓存解析后的教务 JSON）** —— 一期纳入。
- 两者共享「缓存」两个字但完全无关。`OkHttpFactory` **仍然不装 `Cache`**，本端点只是普通的一次 HTTP 调用。

## 4 鉴权接缝

一期的边界：**只做接缝 + 一份最小实现**。完整登录与五家 OAuth 另立 effort。

### 4.1 四个形状

```kotlin
// net/auth/AuthTokenProvider.kt —— 网络层只取 token，不刷新、不判过期
fun interface AuthTokenProvider {
    fun currentToken(): String?
}

// net/auth/SessionInvalidListener.kt —— 网络层只回调，不碰存储
fun interface SessionInvalidListener {
    fun onSessionInvalid()
}

// net/auth/SessionStore.kt —— 存储接缝（一期只有一个实现）
interface SessionStore {
    fun readToken(): String?
    fun writeToken(token: String)
    fun clear()
}
```

三条不可让步的边界：

1. **`currentToken()` 是同步的**。刷新是 provider 自己的事（provider 内部缓存 + 后台刷新，签名不变）。被否掉的：把刷新塞进拦截器（网络层会悄悄承担登录职责）；`suspend` 取值器（一期根本不需要异步刷新，且每个请求都要进协程）。
2. **网络层不直接操作存储**。失效时只 `SessionInvalidListener.onSessionInvalid()`。
3. **但必须提供一个能用的默认实现**：`DefaultSessionInvalidListener` → 调 `MinimalSessionStore.clear()`。被否掉的「纯回调不提供默认实现」：一期上层是空的，回调后什么都不发生 → token 还在 → 下个请求继续 401 → **死循环**。

### 4.2 分区发不发：不一刀切

`backend-plus` 有公开端点，一刀切「没 token 就不发」会把它们堵死。判据是**按 Retrofit interface 分区**，不是按路径字符串猜。

| 分区 | 端点 | 无 token 时 |
| --- | --- | --- |
| 公开 | `/healthz`、`/identity/login/admin`、`/identity/mailcode/send` | **照发**，不挂 `Authorization` |
| 鉴权 | 其余 13 条 | **不发**，本地直接返回失败（`ApiFailure.Http(401, "unauthorized", "缺少凭证")` 形状，不发起网络请求） |

实现方式：`AuthInterceptor` 读一个「当前请求属于哪个分区」的标记。**推荐做法**：给 Retrofit 方法打自定义注解（`@PublicEndpoint`），拦截器读 `Invocation` 的 method annotations 判定 —— 不要用「路径前缀白名单」，因为那会在后端改路径时静默失效。

> ⚠️ **精度提醒（交叉核对发现）**：「3 条公开端点」这个前提**只在可吊销装配（`DATABASE_URL` 非空）下成立**。降级装配用的是 `AuthMiddleware`，它**只放行 `/healthz`**，没有公开路径表（#46 §4.4 实测：降级装配下 `/identity/login/admin` 无票也是 401）。所以「公开」是**装配相关的运行时事实，不是契约常量**。一期的后果：联调时 `/identity/mailcode/send` 在降级后端上**带票才能通**。见 §10。

### 4.3 失效判据表（最容易被写错的一张表）

**为什么不能只看 `code`**：`session_expired` 这一个字符串被后端用在两种完全不同的语义上 —— `internal/server/revocable_auth.go:177` 是**App 会话过期**，`internal/school/jiaowu/handler.go:114-115` 是**上游教务会话失效**。两者同为 401。只看 code 的后果：**学生在教务侧掉线时，App 会把用户踢出登录**。

| 请求所属域 | HTTP | code | 客户端行为 |
| --- | --- | --- | --- |
| `/identity/*` | 401 | `session_expired` / `unauthorized` | **清本地登录态**，回调 `onSessionInvalid()` |
| `/school/*` | 401 | `session_expired` | **不清登录态**，投递「需重新登录教务」事件（一期只记日志） |
| `/school/presence` | 400 / 401 | `invalid_presence` | 不触发登出，按状态码分别处理 |
| 任意域 | 503 | `auth_unavailable` | 服务暂不可用，**不清登录态**，可重试 |
| 任意域 | 429 | `rate_limited` | 不清，提示「操作过快」 |
| 其它/未匹配 | 任意 | 任意（含 `Unknown`） | **保守：不清登录态** |

**三条实现规则**：

1. **判定必须同时读「域前缀 + HTTP 状态码 + code」三者**，缺一不可。`invalid_presence` 同一字面量既用于 400 也用于 401（`presence/handler.go:99` 与 L66/L88），只读 code 无法区分。
2. **前缀匹配必须「最长前缀优先」**。`#52` 的表里写的 `/presence` 是简写，真实路径是 `/school/presence`（`presence.Register` 挂在 `/school` 下）。判定顺序必须是 `/school/presence` → `/school/*` → `/identity/*`，否则 presence 规则永远命不中。（行为上恰好不致命 —— 落到「未匹配 → 不清登录态」也是对的 —— 但这属于碰巧对，不能留。）
3. **这是客户端单方面的协议补丁，不是后端契约。** 后端将来若给其中一个 `session_expired` 正名，这里必须同步改。**规格里不得把它描述成「后端保证」**，代码注释里也要这么写。

### 4.4 并发去重：`AtomicBoolean` 守门

- 首次满足失效条件时：`compareAndSet(false, true)` 成功 → 回调；失败 → 静默丢弃。
- **复位时机（两个条件都满足）**：① 清理完成；② 下次携带**新** token 的请求发起前。
- 被否掉的：不管并发（RN 版当年用 `lastToastAt` + 2500ms 去重 —— 那是**用 UI 层去重掩盖网络层问题**，不照搬）；用 `Mutex` 串行化全部请求（牺牲吞吐换正确性，代价过大）。

一期的现实：没有登录就没有「新 token」，所以复位路径**一期只有测试能覆盖**。这不是缺陷，是 #43 Q2=B（一期不做登录）的必然结果 —— 但实现必须写全，不能留个 `TODO` 让将来的人猜。

### 4.5 `DEV_TOKEN`：只存在于 debug 源集

- `buildConfig = true` 已开启（`app/build.gradle.kts`）。`debug {}` 块里注入
  `buildConfigField("String", "DEV_TOKEN", "\"<本机后端 AUTH_KEY 自签的 token>\"")`。
- **消费方必须在 `src/debug/java/`**（见 §2.3）—— 否则 release 编译不过。
- **token 怎么来**：降级装配（无 `DATABASE_URL`）下，后端用 `cfg.AuthKey` 验签自包含令牌
  `base64url({"sub":"<userID>","exp":<unix秒>}) + "." + base64url(HMAC-SHA256(payload))`，两段 `RawURLEncoding`。
  开发机可以用后端自己的 `AUTH_KEY` 离线签一个。**它只在降级装配下有效**，可吊销装配下会被 401/503 拒。
- 为什么必须做这个兜底：`/identity/login` 现在是 401（后端缺陷），**调试时根本走不通真登录**。没有 `DEV_TOKEN`，网络层连一个需要鉴权的端点都测不了。

## 5 失败与韧性

### 5.1 `ApiFailure` 六类 + 捕获顺序（这是转换器选型的直接后果）

```kotlin
sealed class ApiFailure {
    data class Network(val cause: IOException) : ApiFailure()
    data class Timeout(val cause: IOException) : ApiFailure()
    data class Http(val status: Int, val code: String?, val message: String?, val url: String) : ApiFailure()
    data class Business(val code: String, val message: String) : ApiFailure()
    data class Parse(val cause: Throwable, val bodyPreview: String?) : ApiFailure()
    data object Cancelled : ApiFailure()
}
```

`Parse` **必须独立成类**：后端仍在密集重写，同一端点有两条响应形状；把解析失败混进 `Network`，排查时分不清「网断了」还是「后端改了字段」。

**`ApiCall` 里的捕获顺序（不许调换）**：

```kotlin
try {
    val response = block()                    // block 是 suspend () -> Response<T>
    ...
} catch (e: CancellationException) {
    throw e                                   // ① 绝不吞，见 5.4
} catch (e: SerializationException) {         // ② 继承 IllegalArgumentException，不继承 IOException
    ApiFailure.Parse(e, bodyPreview = null)   //    必须在 IOException 之前
} catch (e: SocketTimeoutException) {         // ③ 读超时
    ApiFailure.Timeout(e)
} catch (e: InterruptedIOException) {         // ④ callTimeout 抛的就是它
    ApiFailure.Timeout(e)
} catch (e: IOException) {                    // ⑤ 其余 IO
    if (e.message == "Canceled") ApiFailure.Cancelled else ApiFailure.Network(e)
} catch (e: Throwable) {                      // ⑥ 兜底，不崩
    ApiFailure.Parse(e, bodyPreview = null)
}
```

六类之外没有「未知失败」这一类，所以第 ⑥ 条兜底进 `Parse`（语义是「拿到了响应但没法变成模型」）。**不要新增第七类**，那是改决议。

### 5.2 超时表

| 项 | 值 | 为什么 |
| --- | --- | --- |
| `connectTimeout` | 10s | OkHttp 默认值，够用 |
| `readTimeout` | **15s** | 给后端首次请求连库留余量 |
| `writeTimeout` | 15s | |
| `callTimeout` | **30s** | **必须设**。OkHttp 默认 `callTimeout=0`（不限总时长），移动网络切换时一个卡住的请求可能永远不返回 |

集中定义在 `net/http/OkHttpFactory.kt`，**不得散落到调用点**。一期的端点全是 identity/school 的轻接口，**不为任何端点单独放宽**（教务类慢接口不在本期）。

### 5.3 重试规则表（含两条硬约束）

| 失败类型 | 可重试 | 次数 | 间隔 |
| --- | --- | --- | --- |
| `Network` | ✅ | 1 | 500ms |
| `Timeout` | ✅ | 1 | 500ms |
| `Http 5xx` | ✅ | 1 | 500ms |
| `Http 4xx` | ❌ | — | — |
| `Business` | ❌ | — | — |
| `Parse` | ❌ | — | — |
| `Cancelled` | ❌ | — | — |

**硬约束 1（无例外）**：`POST` / `PATCH` / `DELETE` **一律不重试，无论状态码是什么**。判定函数签名 `RetryPolicy.shouldRetry(method: String, failure: ApiFailure): Boolean` —— 纯函数，纯 JVM 可测。

**硬约束 2（#47 没写，但不加强就等于没有）**：`OkHttpClient.Builder().retryOnConnectionFailure(false)`。

> 为什么：OkHttp 这个开关**默认是 `true`**，它在「连接层失败、尚未收到任何响应」时会**重发请求，包括 POST**。也就是说即使 `RetryPolicy` 一个 POST 都不放行，OkHttp 自己仍可能把 POST 发两次。要真的做到「POST 绝不重试」，必须全局关掉它，把重试权完全收进 `RetryPolicy`。

不做指数退避（只重试 1 次，退避没有意义）。不用 `Dispatcher` 层重试。

**与既有教训的呼应**：`apps/nongyu-backend-plus/docs/adr/0001` 记了旧实现「网络错误最多重试 3 次、每次 1 秒」与学校侧 15 秒限制冲突。本次定 1 次 / 500ms，比旧实现更保守。

### 5.4 取消：靠 `suspend`，但**这是未验证假设**

Retrofit 的 `suspend` 函数在协程取消时会自动取消底层 `Call`（官方行为），因此**不自持 `Call` 手写 `cancel()`**。

**但这属于「我认为正确」而非「已验证」** —— 必须实测（§7.1），不成立则退回显式持 `Call` 并 `cancel()`。见 §10 待实测第 1 条。

配套三条实现规则：

1. **`CancellationException` 必须重新抛出**，不能转成返回值。否则 `withContext` / `ensureActive` 的语义被破坏，父协程取消后子协程还在跑。
2. `ApiFailure.Cancelled` **只允许**在「调用方主动取消、且确实需要一个值」的外层由调用方构造，**网络层内部不得用它吞取消**。
3. **重试前必须检查 `coroutineContext.isActive`**。否则「取消 → OkHttp 抛 `IOException("Canceled")` → 被判成 `Network` → 触发重试」会出现**取消后请求又发一次**的鬼故事。（这也是 §5.1 第 ⑤ 条要把 `"Canceled"` 单独映射的原因。）

### 5.5 缓存与空响应

- **不装 `Cache`**（内存盘都不装）。一期能打的只有 identity 域几条「当前用户是谁」，全不可缓存；加缓存只会带来「登出后返回旧数据」的风险。
- **空响应**：`Response<Unit>`**只用于真正的空 body**。但 backend-plus **没有真空 body 的成功响应** —— `/healthz` 回 `{"status":"ok"}`、`/identity/logout` 回 `{"ok":true}`、`/identity/mailcode/send` 回 `{"sent":true}`。所以这三个端点都给一个**一行 DTO**，而不是 `Response<Unit>`。
  - 理由：#47 Q6 的意图是「不引入可空 Unit、不让每个调用点判空」，给它一个字段全可空的 DTO 完全满足这个意图，同时把「转换器拿到 JSON body 会不会把 `Response<Unit>` 弄崩」这个不确定性从设计里删掉。
  - 若坚持 `Response<Unit>`，必须先过 §7.1 的 MockWebServer 用例（回 `{"ok":true}` → 断言成功）。这是 #47 Q6 落地时必须补的实测项。

### 6.3 日志与脱敏

- `HttpLoggingInterceptor` **只在 debug 挂**；release 一律 `NONE`。
- 日志走 `Log.d(tag, ...)` 到 logcat，**不落盘**。
- 脱敏三类判据 + 一条结构性规则：

| # | 判据 | 内容 |
| --- | --- | --- |
| ① | 请求/响应头（按名，大小写不敏感） | `Authorization`、`Cookie`、`Set-Cookie`、`Proxy-Authorization` → `***` |
| ② | JSON key（按名） | `password`、`wechatCode`、`ticket`、`cookie`、`goAdminTgt`、`idCardSuffix4`、`token`、`accessToken`、`refreshToken` → `***` |
| ③ | **路径白名单（整体不记 body）** | `/identity/login`、`/identity/login/admin`、`/identity/mailcode/send` |

**③ 是关键**：黑名单对新字段天然失效，而后端仍在密集重写（`loginReq` 里就有 `Password`/`WechatCode`/`Ticket`/`Cookie`/`GoAdminTgt`/`IDCardSuffix4` 六个敏感字段）。登录类端点整体不记 body，是**唯一对未来新增敏感字段免疫**的做法。

### 6.4 拦截器顺序 —— **`#49` 的两拦截器方案按字面实现不了**（交叉核对结论）

`#49` Q3 写的是「`addInterceptor(RedactionInterceptor())` **必须在** `HttpLoggingInterceptor` 之前」。这条**不能按字面实现**，原因是拦截器链的语义：

- `addInterceptor` 里**先加的在外层**。外层先把请求吞进来，处理后 `chain.proceed(请求)` 交给内层。
- 若「脱敏」在外层：它必须把**要往下传的那个 request 对象**的敏感值改掉，内层 logging 才能看到 `***`。但那个 request 就是**真正发出去的请求** —— `Authorization` 变成 `***`，服务端直接 401。
- 若「脱敏」在内层（logging 在外层）：logging 看到的是**未脱敏**的原始请求 → 敏感字段照样打进 logcat。

⇒ 两个拦截器串联，在 BODY 级**必然二选一失败**（改坏请求 / 泄漏）。

**本规格的解法：一个拦截器。**

```kotlin
// net/http/SafeLoggingInterceptor.kt —— 自写，替代 HttpLoggingInterceptor 的 BODY 级
// 1. 在【拷贝】上脱敏：request.newBuilder() / response.newBuilder()
// 2. 读 body 用 peekBody(n)（不消费原 body）
// 3. 只打印，绝不修改真实 request / response
// 4. 命中路径白名单 ③ 时，整块 body 打 "<redacted by path>"
```

- 头脱敏部分是**双保险**：OkHttp 4.12 的 `HttpLoggingInterceptor` 本身对 `Authorization` / `Cookie` / `Set-Cookie` 有内置遮蔽（值打成 `██`），但 `Proxy-Authorization` 不在其列；而 BODY 级它完全不脱敏。（实施时以 4.12.1 源码为准，写一个用例断言一次。）
- 也可以保留 `HttpLoggingInterceptor` 只做 `HEADERS` 级（安全、无需自写），BODY 级交给 `SafeLoggingInterceptor`。**两种都可以，但都不允许「两个拦截器串起来指望后者看到前者的脱敏结果」。**

**装配顺序（`OkHttpFactory`）**：

```kotlin
OkHttpClient.Builder()
    .connectTimeout(10, SECONDS).readTimeout(15, SECONDS)
    .writeTimeout(15, SECONDS).callTimeout(30, SECONDS)
    .retryOnConnectionFailure(false)          // §5.3 硬约束 2
    .addInterceptor(SessionInvalidInterceptor(...))  // 最外：看得到最终响应
    .addInterceptor(AuthInterceptor(...))            // 加 Authorization / 分区短路
    .addInterceptor(SafeLoggingInterceptor(...))     // 最内：只读拷贝
    .build()
```

`SessionInvalidInterceptor` 放最外，因为它要判的是「最终响应」；`AuthInterceptor` 在它之内，保证判据看到的 401 是带过票的结果。

2026-11-11 补充：`AppSignInterceptor` 插在 `AuthInterceptor` 与 `SafeLoggingInterceptor` 之间，只在装配了 `AppRequestSigner` 时挂上。它签的是「请求来自客户端」，不是用户 JWT。`X-Nongyu-Signature` 必须进日志脱敏名单。

### 8.2 并行 / 串行关系

```text
N1 ──┬── N2 ──┬── N3 ──┐
     │        └── N4 ──┼── N6 ── N7
     └── N5 ───────────┘
```

- **可以同时开工（互不连边）**：
  - **N2 ∥ N5** —— 一个写 `net/core` 纯逻辑，一个写 `net/auth` + `res/xml`，**文件零交集**。
  - **N3 ∥ N4** —— 一个写 `net/http`，一个写 `net/model` + `net/api` + `test/resources`，**文件零交集**。
  - 即：**最大并行度 = 2**。N1 本身很短（半天级），不必再拆。
- **必须串行**：
  - **N1 → N2 / N5**：N2/N4 的 DTO 要 serialization 插件才能编过；N5 要 `security-crypto` 依赖才存在。这是**编译级依赖**，不是文档约定。
  - **N2 → N3**：拦截器直接用 `ApiFailure`（`SessionInvalidInterceptor` 要判失败类型）、`SessionInvalidRules`（判据）、`UrlBuilder`。**N3 不允许自己再写一份判据** —— 那就是两份真源。
  - **N2 → N4**：`ApiErrorCode` 常量表放 `net/core`（它是纯字符串、零依赖），`api/` 层要引用它。若强行让 N4 先并行，会出现两处错误码常量。
  - **N3 + N4 + N5 → N6**：门面要同时持有 http 客户端、三个 interface、session store 才能装配。**三个都到位之前 N6 只能写一半，合拢时会打架**（同一个 `NetHolder.kt` 被三方改）。
  - **N6 → N7**：验收的对象必须是完整链路。而且 N7 有一条**只能做一次**的动作：删掉 `RetrofitSpikeProbe.kt` 后重测 R8 —— 探针还在的时候，`usage.txt` 显示整条库链被 REMOVED，**任何 keep 结论都是假的**。

### 8.3 为什么 N6 里必须删掉 `RetrofitSpikeProbe.kt`

它原先在 `app/src/main/java/com/nongyu/appplus/net/RetrofitSpikeProbe.kt`，是 #48 的编译期探针，**不被任何业务代码引用**。它的 JSON 配置（`ignoreUnknownKeys` / `explicitNulls`）已迁到 `net/model/NetJson.kt` 的正式 `Json` 实例。

> ### ⚠️ 本条假设已于 N6 实测**证伪**（2026-11-09）
>
> 本节原先写：「**删掉它，是让 R8 结论从「空洞的成功」变成「真实数据」的前提条件。**」
>
> **这是错的。** 删掉探针后重新构建 release，R8 **仍然**把整条库链删光了：
>
> ```
> mapping.txt   okhttp3 kept=0 / retrofit2 kept=0 / kotlinx.serialization kept=0
> usage.txt     okhttp3 removed=326 / retrofit2 removed=120 / serialization removed=364
> ```
>
> **真正的原因**：R8 从**入口点**（`MainActivity` / Manifest 组件）出发做可达性分析。
> 删掉探针后网络层确实是真实实现，但 `MainActivity` 只 import `skin.FileSkinSource`、
> `ui.NongyuApp`、`ui.theme.*` —— **没有任何业务代码引用网络层**，
> 所以 `NetHolder` / `NongyuApi` 及其下游整体不可达。
>
> **修正后的判据**：让 R8 结论变真的充要条件是「**有业务代码从入口点可达地引用网络层**」，
> 而不是「删掉探针」。
>
> **推论**：一期按 #50 Q6「网络层不接 UI」，**在结构上就不可能**满足这个条件。
> 因此「R8 keep 需求」在一期**无法验证**，继续挂在 §10 的待实测清单，
> 直到网络层被真实接入。详见 `docs/specs/网络层-N6-实施记录.md` §3。

## 9 跨票交叉核对（四对，逐对给结论）

### 第 1 对：转换器选型 vs 失败分类 —— **能独立，但靠的是客户端 catch 层，不是 Retrofit**

`ApiFailure.Parse` 可以真的独立，机制如下：

- kotlinx.serialization 抛的是 **`SerializationException`**（以及 `MissingFieldException` 等子类）。它**继承 `IllegalArgumentException`，不继承 `IOException`** —— 这条继承关系是 `Parse` 能独立的前提。
- Retrofit 的 `Converter.Factory` **不会**把反序列化失败变成 `isSuccessful = false`。解析发生在拿到 2xx 之后，异常**从 `suspend` 调用点抛出**，而不是变成一个带 errorBody 的 `Response`。
- 所以「`Parse` 独立」的落点是 **`net/core/ApiCall.kt` 的 catch 顺序**：先 `SerializationException` → `Parse`，再 `IOException` → `Network`/`Timeout`。**顺序不能反**（`SerializationException` 不是 `IOException`，反了也不会误捕，但 `Throwable` 兜底必须最后）。
- **推论**：`Converter.Factory` 里不需要、也不应该自己 catch 异常再做转换 —— 那会把分类逻辑拆到两处。工厂只负责「用我们定好的 `Json` 建出来」。

⇒ **结论：不矛盾，可实现。** 但 #47 只定了「类型」，没定「在哪捕获」；本规格把落点钉在 `ApiCall`，并新增两条硬约束（`CancellationException` 必须重抛、`Throwable` 兜底进 `Parse`）。

### 第 2 对：落点/装配 vs ADR-0006「冷启动不碰网络」 —— **满足**

- 启动路径现状：`MainActivity.onCreate` → `enableEdgeToEdge()` → `FileSkinSource.resolve()`（同步本地磁盘）→ `setContent`。**没有网络入口**。
- `NetHolder.api` 是 `by lazy` → **没人访问就不构造**。全工程无 `Application`、无 `ContentProvider`、无 `Worker`，所以不存在「隐式提前初始化」的路径。
- OkHttpClient/Retrofit 的构造**不做网络 IO**，只有 URL 解析与对象创建。
- **但要加三条守卫**（已写进 §2.4）：① 禁止在 Composable/Activity 访问 `NetHolder`；② `MinimalSessionStore` 自身也必须惰性打开（Keystore 初始化是磁盘+IPC，不能因为「顺手在 NetHolder 里 new 一个」而跑到启动线程上）；③ 将来的会话恢复与皮肤下载器（#53）必须在首帧后。

⇒ **结论：不矛盾，但「惰性」只保证「没人调用就不构造」；真正的风险是将来有人在启动路径上访问它。** 守卫要写进代码注释，不能只写在这份文档里。

### 第 3 对：鉴权存储 vs `allowBackup=true` —— **方向正确，但 `#49` 的片段不足以防崩**

「在 `data_extraction_rules.xml` 里排除加密存储文件」**必要但不充分**。四个缺口：

1. **`data-extraction-rules` 有两个段，`#49` 只写了 `<cloud-backup>`，漏了 `<device-transfer>`**。API 31+ 的换机迁移（D2D）走后者，只排云备份的话，密文照样被带到新机 → 新机 Keystore 里没有对应 Key → 首次读取解密失败 → **崩**。（§6.5 已给补全后的 XML。）
2. **`allowBackup=true` 下两个文件都要写**：`backup_rules.xml`（`full-backup-content`，API ≤30）+ `data_extraction_rules.xml`（API 31+）。只写一个，另一条备份路径就是敞开的。
3. **排除规则不可能穷举所有备份通道**（ADB、厂商云、部分工具的私有通道）。所以**读取侧必须自己容错**：`MinimalSessionStore.readToken()` 要 catch 解密相关异常（`GeneralSecurityException` / `AEADBadTagException` / `InvalidKeyException` 这一族），**把「解不开」当成「没有 token」并清空文件**。这条不做，排除规则一旦被绕过就是崩。
4. **`path` 不要用 `@string/...`**（理由见 §6.5）：当前 `strings.xml` 没这个字符串，且资源引用在备份规则 XML 里是否被解析未取证。改字面量 + Kotlin 常量单一真源。

**换设备恢复会发生什么**（期望行为，写进验收）：

| 场景 | 期望 |
| --- | --- |
| 同一设备重装 | 备份里有密文但 Keystore Key 已随卸载丢弃 → 解不开 → **当作无 token，静默进入未登录态** |
| 换机（云备份恢复） | 被 exclude 排除 → 该文件不存在 → 无 token → 未登录态 |
| 换机（D2D 直传） | **只有补了 `<device-transfer>` 才如此**；否则密文到位、Key 不在 → 解不开 → 走第 3 条的容错 |
| 任何上述场景 | **不得崩溃**；用户重新登录即可 |

⇒ **结论：方向对，但要补 `<device-transfer>` + 读取侧容错 + 放弃 `@string` 引用。** 三条都不是「改决议」，是决议没写到的空白；一期没有登录，所以实际风险低，但接口必须**按最坏情况写成安全的**。

### 第 4 对：网络平面范围 vs backend-plus 覆盖度 —— **一期能打的是「登录之外的非业务端点」**

`#46` 的量化结论：**12 组完全没有 / 2 组部分有 / 0 组齐全**，且唯一像登录的那条（`POST /identity/login`）因尾斜杠不匹配**恒 401**。

把「后端有啥」与「客户端能构造啥」叠起来，一期的真实可打集合：

| 端点 | 装配要求 | 一期可达 | 说明 |
| --- | --- | --- | --- |
| `GET /healthz` | 任何装配 | ✅ | 已实机确认 200；不经限流/RequestID |
| `POST /identity/mailcode/send` | **可吊销装配**才免票 | ⚠️ | 降级装配下需带票 |
| `POST /identity/login/admin` | 需 DB（签发会话） | ⚠️ | 路由存在，成功路径走不通 |
| `GET/POST/DELETE /school/*` 6 条 | Bearer；降级装配即可 | ✅ | #46 用降级装配自签 token 实测 `/school/address` 200 |
| `GET/POST /school/presence` 2 条 | Bearer | ✅ | |
| `POST /identity/login` | — | ❌ | 后端缺陷 401 |
| `POST /identity/logout` | Bearer + `CtxSessionID` | ⚠️ | 降级装配无会话可吊销 |
| `GET /identity/me`、`PATCH /identity/me/profile`、`GET /identity/users/:studentNo` | **仅 `DATABASE_URL` 非空时注册** | ❌ | 降级装配下**返回 text/plain 404** |

**三条对规格的硬影响**：

1. **门面只暴露 3 个方法**（`healthz` / `sendMailCode` / `loginAdmin`），`SchoolApi`/`PresenceApi` 只定义不构造 —— 与 `#50` Q2 一致，但**理由要说准**：不是「身份域更完整」，而是「school 域的语义（地址编码/换票）不属于本期业务，且它需要直连学校那套 future 票」。
2. **「登录 → 拿 token → 打业务」这条端到端链路现在是断的**，断点在后端不在客户端。规格必须显式写这句，否则实现者会反复试错、以为是自己的 bug。
3. **一期真正被验证的只有「公开端点 + 自签 token 的 school 端点」**。`ProfileDto` 一族虽然照契约写好了，但**没有任何一次真实响应验证过它们**（#46 §8.2：`DATABASE_URL` 分支的响应一个都没观测到）。这也决定了 §7.1 里 DTO 只能靠 fixture 测，不能靠真后端。

⇒ **结论：不矛盾（`#50` 的门面范围与 `#46` 的缺口一致），但「可打端点」与「可验证端点」是两回事**，规格不能把「interface 定义好了」当成「能用」。

### 10.2 ⚠️ 最重要的一条：`#48` 的「构建通过是空洞的成功」

三条转换器路线在**不加任何 keep** 的情况下都能 `assembleRelease` 成功，但探针类 `RetrofitSpikeProbe` 不被任何业务代码引用，R8 把整条库链删了：

```

⇒ **「R8 需要什么 keep」本次测不出来。** 这不是「自带规则够用已经成立」，是「本次根本没测到」。规格里、代码注释里、后续票里，**都不许写成「R8 无负担」或「自带规则够用已成立」**。它是一条必须在 N7 重测的**验收项**。

同类假象还有一个：`security-crypto:1.1.0` 接入时 release 只 +184 B，因为 R8 把 1,432 个 security/tink 类全裁了。真实增量同样未测。

> 一期按 #50 Q6「网络层不接 UI」在结构上做不到，因此：
> **「R8 keep 需求」一期无法验证，验收时不得声称已验证。**

### 10.4 已决（原「需要维护者拍板的一条」）

**`androidx.security:security-crypto:1.1.0` —— 维护者已于 2026-11-09 拍板引入。**

- **结论**：引入，`implementation` 作用域，版本钉 **1.1.0**（实测 `minCompileSdk=34` / `minAGP=8.1.1`，本工程 36 / 9.2.1 均有余量）。
- **理由**：已有成熟实现优于手写约 100 行 Keystore + AES-GCM。手写方案虽零新依赖，但要自管 IV、Key 失效、R8 keep，且更容易在备份与换机恢复上出错。
- **已接受的代价**：拖入 `tink-android:1.8.0`；AndroidX 有「不再推荐用于新代码」的说法（若将来正式废弃，另立 effort 迁移）。
- **仍必须做的三件事**（与选型无关，是 §9 第 3 对的结论）：
  1. `data_extraction_rules.xml` **同时**排除 `<cloud-backup>` 与 `<device-transfer>`；
  2. 排除路径用字面量 + Kotlin 常量单一真源，**不要**用 `@string/`（该字符串当前不存在，且 `path` 是否解析 resource ref 未取证）；
  3. **读取侧必须容错**：解不开 = 视为无 token 并清空，不得抛异常。

## 11 本次不做（Out of scope）

对齐地图 #41 的 Out of scope，任何实现者不得自行扩大范围：

- **完整登录流程与五家 OAuth**（QQ / 微信 / Google / X / Apple）—— 见 `docs/research/mobile-oauth-landing.md`，另立 effort。本期只做接缝。
- **客户端直连学校**（教务 / WebVPN：cookie、`wengine_vpn_ticket`、GBK 页面、15s 节流与串行）—— 独立网络平面，约束见 `apps/nongyu-backend-plus/docs/adr/0001`。
- **配置 / 皮肤目录接口** —— 归皮肤地图 #20，且受 ADR-0006 约束。
- **埋点上报**（`apps/nongyu-node-track-server`）—— 独立契约、独立平面。
- **OkHttp `Cache`（HTTP 层响应缓存）、证书固定、分页、上传下载、SSE / WebSocket 流式** —— 一期全不做（pinning 是有意推迟，见 §6.2）。⚠️ 这与「业务层回传数据缓存端点」是两件事，后者已纳入一期，见 §3.6。
- **状态管理 / DI / 路由 / ViewModel** —— 本工程尚无（无 `Application`、无 `ViewModel`、无路由库）。
- **被 UI 调用** —— 一期网络层不接任何 UI（#50 Q6）。
- **`backend-plus` 自身的两个缺陷**（`/identity/login` 尾斜杠 401、`/identity/users/:studentNo` 无角色判定）—— 属后端仓问题，应在 `NongyuSystem/nongyu-backend-plus` 另建 issue，不作为本期子票。
- **R8 keep 的最终结论** —— 本期只建立重测条件（删探针 + 真实引用），结论归 N7。
