# 活动层（H5 节日页）：不更新 APK 即可临时上线节日展示

> 状态：**已定稿，待实施**（2026-11-09）。
> 本文件是唯一真源，对应 GitHub issue。
> 本文**不含具体文件路径与代码片段**（按 `/to-spec` 模板约定），落地时以本文件的决策为准。

---

## Problem Statement

农屿要过节日（万圣节等）：主界面中间飘出鬼魂、底部出现节日装饰，用户点开能看到一整页节日内容。但现实是**每次改一点视觉都要发一次 APK**——版本号递增、构建、传 Release，一个节日彩蛋走完这套流程，节日已经过去了。

同时维护者提了两个必须满足的前提：

1. 用户**不需要更新包**就能看到这次节日内容；
2. 节日结束后能**及时下线**，不让过期内容继续出现或者变成一个死链接。

还有一层现状约束：客户端的 release 变体**连生产域名都还没定**（`NetConfig.BASE_URL` 是空串，网络层首次装配会直接抛异常）。任何依赖服务端的功能，在 release 包里今天都跑不起来。

---

## Solution

新增一个**活动层**：一套由服务端可配置、客户端本地判定的节日活动能力。

- 运营在后台配置「当前有哪些活动、各自什么展示策略、H5 页面在哪个 URL」。
- 客户端冷启动时**只读本地缓存**判定要不要显示入口，首帧即可正确；**首帧之后**再异步联网刷新配置，但**以启动周期为粒度生效**，绝不打断当前会话。
- 命中则主界面右下角出现一个节日悬浮入口；点开是一个**全屏 WebView 页面**，页面自己负责全部视觉（背景、飘动的鬼魂、底部装饰），原生只提供一个节日配色的加载占位页。
- H5 与客户端之间只有一条**受 origin 白名单约束**的消息通道，v1 只暴露一个「关闭页面」动作。
- 全部决策逻辑压在一个**纯逻辑判定器**里，四条策略轴、覆盖优先级、「只出一次」的计数全在纯 JVM 单测里覆盖。

用户感知到的结果是：节日当天打开 App 就有氛围，点进去有内容；节日过后它自己消失；断网时它就是不存在。

## User Stories

**看到入口**

1. 作为用户，我想在节日期间打开 App 就看到一个节日入口，以便知道现在有活动，而不用我先去某个菜单里翻。
2. 作为用户，我想这个入口**不遮挡**底部导航和中间的农小屿球，以便我照常使用 App。
3. 作为用户，我想入口的位置和大小在不同屏幕宽度下都合适，以便小屏不挤、大屏不飘。
4. 作为用户，我想在节日结束后这个入口自动消失，以便主界面回到干净状态。
5. 作为用户，我想这个入口永远不要出现在我被强制打断的场景（比如自动弹全屏），以便我打开 App 是为了用课表而不是看广告。

**打开页面**

6. 作为用户，我想点入口后看到一个全屏节日页面，以便沉浸地看到完整内容。
7. 作为用户，我想页面打开时不是一片白，而是一个节日配色的加载占位，以便网络慢的时候我也知道它在加载。
8. 作为用户，我想按系统返回键能退出这个页面回到主界面，以便我不会被困在里面。
9. 作为用户，我想页面里也能有一个自己的关闭方式，以便我想退出时不用非得找返回键。
10. 作为用户，我想断网时点入口不会卡在一个白屏上，而是很快回到主界面，以便我知道现在看不了、同时 App 还能用。
11. 作为用户，我想在页面里点了一个外部链接时**不会**被带到一个陌生的网页里，以便不被钓鱼页面冒充。

**只出现我该看到的**

12. 作为用户，我想「只出现一次」的活动真的只出现一次，以便它不会变成一个天天来烦我的东西。
13. 作为用户，我想「每个启动周期最多一次」的活动在我在 App 内切 Tab、点开又关掉之后不再重复弹出，以便我的操作不被打断。
14. 作为用户，我想在被服务端撤回到的活动，至少在我**下次打开 App** 时就不再出现，以便下线的活动不会长期残留。
15. 作为用户，我想正在看的页面不会在看的途中被强制关掉，以便我不会看到一半被踢出去。
16. 作为用户，我想手动关掉的活动**本次启动内**不再出现，以便我明确表达「现在不想看」。

**条件与身份**

17. 作为未登录用户，我想节日入口照样能看到，以便彩蛋不因为没登录就看不到。
18. 作为未登录用户，我想需要登录的活动**不**对我出现，以便我不会点进去发现要点登录。
19. 作为老版本客户端用户，我想不兼容的活动不要出现在我面前，以便我不会点进去看到一个坏页面。
20. 作为用户，我想活动页面的配色跟农屿的品牌色一致，以便它看起来像这个 App 的一部分，而不是嵌了个别人的网页。

**运营侧**

21. 作为运营，我想在不发版的前提下上线一个新节日，以便节日当天就能上。
22. 作为运营，我想配置这个活动**出不出、什么时候出、给谁出、出几次**，以便同一个功能能覆盖「必定出 / 条件出 / 次次出 / 只出一次」这些不同玩法。
23. 作为运营，我想紧急下线一个活动，以便内容出问题时能马上止血。
24. 作为运营，我想下线不需要用户升级 App，以便止血速度不受发版周期限制。
25. 作为运营，我想同一时刻只会有一个活动生效，以便我不用去调「几个活动撞了怎么排序」。

**将来（本期不做，但要留得住）**

26. 作为用户，我想以后能在 App 里设置「不要再显示节日效果」，以便我不喜欢这类氛围时能永久关掉。
27. 作为用户，我想我对频率/强度的偏好能覆盖运营配置，但运营设的条件（时间窗、是否需登录、版本范围）不能被我自己打开，以便我不会把已经下线的活动翻出来看到一个坏页面。
28. 作为开发，我想将来加发奖、签到这类能力时能扩消息通道，而不用重做整个容器，以便这个功能能长大。

## Implementation Decisions

### D1. 承载形态：真 WebView 加载远端 H5，独立全屏页

- H5 由远端 HTTPS 托管，客户端**不在 APK 内打包** H5。
- 节日页是**独立全屏页面**，不是叠加在主界面上的透明层。
  - 决定性理由：WebView 是矩形、不透明、且吞掉全部触摸事件。「中间飘鬼魂、底部有装饰」在 H5 自己的画布里用 CSS 定位同样做得到，而透明 WebView 叠在主界面上会和现有 AI 球的指针手势、底栏点击**直接打架**，还会掉帧。
- **明确不做**：透明 WebView 叠加、替换某个 Tab 的内容、Custom Tabs 跳出 App。

### D2. 主界面入口：右下角悬浮按钮

- 入口是主界面上的一个**悬浮圆形按钮**，位于右下角，避让底部导航栏高度。
- 「右下角」是主界面上**唯一还空着的角**：左上/左下已有雷达波与球体动画区域；右上角将来属于日程操作（既有 wayfinder 地图里的第 4 步），提前占用会撞车。
- 入口尺寸参与现有的 `uiScale` 自适应（以 411dp 屏宽为基准、夹在 0.85–1.25），与底栏、球体保持同一套缩放比例。
- 入口**不做**：不自动弹出全屏页、不替换 AI 球、不改变底栏结构。

### D3. 展示策略：三个正交轴 + 一个开关

策略由服务端下发，客户端只执行。**不做自由组合的面板**，固定为三个轴：

| 轴 | 取值 | 语义 |
|---|---|---|
| **频率** | `every_launch` / `once_ever` / `once_per_launch_session` / `daily` | 这个活动能出现几次 |
| **条件** | 时间窗（起止时刻） / 仅已登录 / 版本区间（`minAppVersion`、`maxAppVersion`） | 这个活动对谁、什么时候有效，三者可**同时**要求（与关系） |
| **强度** | `entry_only` / `auto_open` | 只显示入口，还是判定命中后自动进入全屏页 |
| **开关** | `enabled` | 总闸。关闭即全端下线 |

- 「必定出」= 无条件 + `every_launch`。
- 「条件出」= 条件轴非空。
- 「次次出」= `every_launch`。
- 「只出一次」= `once_ever`。
- **同一时刻只有一个活动生效**：服务端配置接口只返回**单个当前活动对象**，不做列表。这样从根上避免了「多个活动同时命中怎么排序」这个问题。
- `auto_open` 强度虽然保留在模型里，但**本期客户端按 `entry_only` 执行**；`auto_open` 的落地留到有真实需求时再议（它意味着打断用户正在做的事，需要单独论证）。

### D4. 覆盖优先级：分层，不是二选一

服务端策略与（将来的）用户偏好冲突时：

- **条件轴与 `enabled` 是运营独占**：用户不能把运营关掉的活动打开，也不能绕过时间窗/登录/版本要求。理由：这些是服务端事实，绕过会让用户打开一个已下线、404 或白屏的页面。
- **频率与强度可被用户覆盖**：这是用户体验偏好，用户可以「少看一点」。
- 用户覆盖层本期**只落数据模型、存储与读取优先级，不做 UI**（见 D10）。

### D5. 判定时机：冷启动同步读本地缓存，首帧即正确

- 冷启动**同步读本地**「策略缓存 + 已出计数」，纯本地磁盘读，**不碰网络**——这与 ADR-0006「冷启动只读本地、绝不碰网络」相容。
- 判定命中 → 首帧就有入口。
- **首帧之后**异步拉取最新配置写回本地缓存。
- **纪律：配置变更以「启动周期」为粒度生效**，不打断当前会话、不首帧后跳变。这条与 ADR-0006 的「换皮以启动周期为粒度」同构，也和 ADR-0006「不允许首帧后跳色」的精神一致。
- 正在全屏页里的用户**不被打断**，撤回在下次启动生效。
- 冷启动读缓存失败 / 文件损坏 / schema 版本不符 → **一律判为「不展示」**，不重试、不联网兜底。彩蛋的失败方向必须是「消失」，不能是「卡住启动」。

### D6. 「出过几次」的状态只存本地

- 本地持久化，与策略缓存分开存放（计数在活动上线期间必须稳定，不能被策略刷新的写入顺手覆盖）。
- 服务端**不**记录次数。理由：配置接口是匿名公开的（D8），未登录用户无法记账；而「清 App 数据可以重看一次彩蛋」完全可以接受，为此引入一套服务端计数与跨设备同步不划算。
- 计数键包含活动标识，活动下线后其计数可随 LRU 清理。

### D7. WebView 能力与安全边界

| 项 | 决策 | 理由 |
|---|---|---|
| JavaScript | **开** | H5 内容本身需要 |
| 与原生通信 | **只走 `addWebMessageListener`（origin 白名单）**，**禁用 `addJavascriptInterface`** | `addJavascriptInterface` 会注入**所有 frame** 且**没有任何 origin 概念**，用它锁 origin 是做不到的。这是本 spec 最容易被写错的一条 |
| 通道注入范围 | 只在配置下发的那个精确 origin（scheme + host + port）上注入，**禁止 `*` 通配** | 平台级约束，不依赖我们自己写检查 |
| v1 暴露的方法 | **只有一个「关闭页面」** | H5 要能自己收场，否则用户只能靠返回键。加方法比先开一堆再收回安全 |
| WebView 内导航 | 只允许停留在白名单 origin；任何离开白名单的导航**一律拦截**，不外跳、不留 WebView | 防止 H5 里点一个链接就被带进陌生页面 |
| DOM Storage | **关** | 不记状态就没有脏数据与跨活动污染问题；「只出一次」的计数在原生侧（D6），不需要 H5 自己存 |
| 明文 HTTP 子资源 | **禁止**（混入即拦截） | release 无明文放行，http 子资源会直接加载失败；也避免供应链降级 |
| 文件访问 / `file://` | **禁止** | H5 不需要读本地文件 |
| 加载失败 | **自动关闭回到主界面**，最高 8 秒超时 | 彩蛋失败最正确的姿势是消失，不是留个白框 |
| 调试开关 | **仅 debug 源集**可配置成加载本地 http 页面 | 与既有的 debug 网络安全配置同一套边界，release 里这个符号根本不存在 |

### D8. 后端：匿名公开的单对象配置接口

- 新增一个**匿名可访问**的配置接口（与 `/healthz` 同一层级的公开性），无需登录态。理由：彩蛋不该要求登录，未登录用户也应能看到节日氛围。
- 返回**单个当前活动对象**（没有活动时返回空/`null`），字段至少包含：
  - 活动标识、`schemaVersion`
  - `enabled`
  - 频率轴、条件轴（时间窗、是否需登录、版本区间）、强度轴
  - H5 页面 URL、页面版本号、内容哈希
  - 展示名与封面（运营侧展示用）
- 客户端按 `schemaVersion` 判能否解析：主版本高于客户端支持 → 整个对象忽略、回落「不展示」并记日志；同主版本内未知字段一律忽略（`ignoreUnknownKeys`），不因加字段而硬失败。
- **不新增**任何静态文件路由。`backend-plus` 目前 16 条路由里没有任何静态资源服务，为一次节日给它加文件托管是长期维护负担。

### D9. H5 托管：对象存储 / CDN

- H5 页面由前端同学构建后上传到对象存储或 CDN，客户端只从配置里拿 URL。
- 强制要求：**HTTPS**、稳定可直接访问的 URL、内容哈希客户端可校验。
- 不做：APK 内打包、Service Worker 离线包、复用皮肤包的下载/校验通道。
  - 理由：皮肤包通道是为「进 `filesDir` 被原生解包消费」设计的，而 H5 是交给 WebView 的整页资源；硬套会把这份 spec 膨胀成「H5 资源分发系统」，与皮肤包项目高度重叠，应当**另立一份 spec**。

### D10. 用户覆盖层：本期只留位，不做 UI

- 数据模型、本地存储 schema、读取优先级（D4）本期完整设计并落地。
- **App 内设置入口不做**。当前全仓没有设置页、也没有偏好持久化，把设置页塞进这份 spec 会让边界失控。
- 将来的落点建议在「个人」Tab 下的独立设置页；届时只需接上已设计好的覆盖层，**不需要改判定器逻辑**。

### D11. 视觉：只把品牌色注入 H5

- 原生把当前色板的**品牌色单个值**通过 URL 参数传给 H5。
- H5 其余配色与动效自治。
- 不做的：全量色板 token 注入。理由：全量注入会让 H5 与皮肤包的每个字段耦合，改一个 token 就得回来改 H5；只给品牌色就够让它「像农屿」。
- 品牌色取值来源是现有 `NongyuColors.brand`，不新造色值。

### D12. 加载体验：原生占位页 + 缓存优先

- 点开入口后立刻显示一个**节日配色的原生占位页**（含品牌色、加载指示），放在 WebView 下层。
- WebView 采用「优先用缓存、缓存没有才走网络」的模式，缓解二次打开的白屏。
- 断网：走 D7 的超时→自动关闭。
- **不做**真正的本地预缓存（见 D9 的理由）。

### D13. 入口的视觉与动效

- 悬浮按钮带最轻微的入场/呼吸动效即可，**不得**引入会与雷达波、dim、球体动画抢合成层的长驻动画。
- 按钮外观由服务端配置决定不了（本期不做远程图片），用内置的节日图标集合 + 品牌色；服务端只控制「显不显示」。

### D14. 前置阻塞项（硬条件）

- **release 变体的 `NetConfig.BASE_URL` 必须先生效**。当前是空串，网络层首次装配会抛「release 变体未配置 BASE_URL」，意味着这个功能在 release 包里做完了也跑不起来。
- 因此本功能的**验收必须在定好生产域名之后**进行；在此之前只能在 debug 变体上验证。
- 这一条要写进实施 ticket 的前置，不能默认它「总会被顺便解决」。

## Testing Decisions

### 什么算好测试

- **只测外部行为，不测实现细节**：断言「给定这些输入，该不该展示、计数变成几」，不断言内部用了什么数据结构、走了哪个分支。
- 沿用本仓既有纪律：纯逻辑层**不得 import `android.*`**（`net/core` 与 `skin` 都是这样，纯 JVM 单测才能覆盖决策逻辑）。

### 接缝（只有一个新增）

**策略判定器**（纯 Kotlin，无 Android 依赖）——整份功能唯一的决策核心，输入输出都是纯数据：

- 输入：服务端策略对象 + 本地已出计数 + 当前时间 + 已登录与否 + 当前 App 版本 + （将来的）用户覆盖偏好
- 输出：是否展示 + 更新后的计数

这一个接缝覆盖了四条策略轴、条件轴的三项与关系、覆盖优先级、以及「只出一次」的全部组合。

### 测什么

1. **频率轴**：`every_launch` / `once_ever` / `once_per_launch_session` / `daily` 在「从未出过」「已出过 N 次」「跨天」下的判定。
2. **条件轴**：时间窗内/外/边界时刻；仅已登录在登录与未登录下的差异；版本区间在低于下限、区间内、高于上限、缺省为空时通过。
3. **条件轴组合**：三个条件同时要求时，任一不满足即不展示。
4. **覆盖优先级**：用户偏好不能打开运营关闭的活动；不能绕过时间窗/登录/版本；但可以降低频率。
5. **计数推进**：展示后计数按频率轴语义正确推进；未展示时计数不变。
6. **策略解析降级**：`schemaVersion` 主版本过高 → 忽略；未知字段 → 忽略且不影响其他字段。
7. **缓存失败**：文件缺失 / 内容损坏 / schema 不符 → 一律判「不展示」，不抛异常。

### 不测什么（真机手工验证）

WebView 容器、原占位页、超时关闭、入口按钮的视觉与避让。理由：与既有做法一致——本仓对 UI 与 R8 相关行为一直靠真机手工过一遍（见 `AGENTS.md` 的发版前手工清单）。

### Prior art

- `app/src/test/` 下 `net/core` 与 `skin` 的纯 JVM 单测：同样把全部决策收进纯逻辑类，输入输出都是数据类。
- `ColorPayloadParserTest` / `SkinPackLoaderTest`：同类「解析 + 逐项回落 + 不因单点失败丢整体」的测试形态，本功能的策略解析降级可以直接照抄这种做法。

## Out of Scope

- **App 内设置页与用户偏好 UI**：只留数据模型、存储与读取优先级（D10）。
- **H5 离线预缓存 / 资源分发系统**：那是皮肤包项目的延伸，需另立 spec（D9）。
- **远程下发的入口图片 / 动态图标**：本期入口图标内置，服务端只控显隐（D13）。
- **`auto_open` 强度的落地**：模型保留，客户端本期不执行（D3）。
- **多活动并存与排序**：配置接口只返回单个对象，不支持同时多个（D3）。
- **按地区 / 设备 / 人群定向**：会要求客户端上报这些属性，与「匿名公开」冲突（Q19 已否）。
- **服务端计数与跨设备同步**：只存本地（D6）。
- **H5 与原生之间的除「关闭」以外的任何消息**：签到、发奖、埋点上报均不做（D7）。
- **JS bridge 的版本协商协议**：v1 只有单方法，不需要协商。
- **`backend-plus` 的静态文件托管能力**：不做（D8）。
- **生产域名的具体取值**：属于网络层的地盘，本 spec 只把它记为前置阻塞（D14）。

## Further Notes

### 为什么不用现有的皮肤包通道

现有皮肤包体系（ADR-0003/0005/0006）已经解决了「不更新 APK 换视觉」，看起来很像。但它是为**原生消费的二进制资源**设计的：进 `filesDir/skins/{packId}/{version}/`、按资源逐项回落、冷启动只读本地。H5 是**整页交给 WebView**的东西，塞进它需要新定一份 bundle 契约与解包路径。第一版节日彩蛋用远端 URL 最省，等真需要离线节日页时再谈复用。

### ADR 关系

- 与 **ADR-0006**（冷启动只读本地、不碰网络、不允许首帧后跳变）**相容**：判定走本地缓存，网络刷新在首帧后，变更以启动周期为粒度生效。
- 与 **ADR-0007**（性能优化排序与放行门槛）的关系：本功能**不得**往冷启动路径上加网络，只增加一次小文件同步读。实施时这次读的耗时应当能被量化，若明显劣化冷启动，回落方案是「缓存读失败就当不展示、不重试」。
- 本功能**不修改**任何现有 ADR。若将来要引入 H5 资源分发，那时才需要新的 ADR。

### 术语

本文新增的领域词，落地时应补进 `GLOSSARY.md`：

- **活动（Campaign）**：一次节日展示的完整配置单元，由服务端下发。
- **活动层（Campaign Layer）**：承载活动的客户端能力总称（入口、全屏页、判定器、缓存）。
- **展示策略（Display Policy）**：三个轴（频率 / 条件 / 强度）+ 总开关。
- **策略判定器（Policy Resolver）**：纯逻辑决策核心。
- **展示计数（Impression Count）**：本地记录的「已展示次数」，驱动频率轴。

注意与既有词的边界：**活动** ≠ **皮肤**（皮肤换的是 App 内视觉资产，活动是一段有时限的内容）；**活动** ≠ **主题**（主题只管颜色）。
