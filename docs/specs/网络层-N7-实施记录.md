# N7 实施记录：真实 R8 数据（首次有效）与启动探针

> 分片 N7（验证与验收）。规格 `docs/specs/网络层.md` §7、§8.1。
> 日期 2026-11-09。状态：**R8 结论首次成立**；真机与 Keystore 仍未验。

## 1 为什么需要先做「启动探针」

N6 实测发现（见 `网络层-N6-实施记录.md` §3）：**网络层没有任何从入口点可达的引用时，
R8 会把整条库链删光**，此时 `assembleRelease` 一律成功但什么也没验到。

所以 N7 的第一步不是「跑验收」而是**造一个可达的真实调用点**。

### 实现：`net/NetStartupProbe.kt`

```kotlin
object NetStartupProbe {
    fun schedule(owner: LifecycleOwner, context: Context)   // 等首帧后再发
    internal suspend fun runProbe(context: Context)          // 真正发请求，不抛异常
}
```

在 `MainActivity.onCreate` 的 `setContent {}` **之后**调用。

### 三条守住的边界

1. **必须在首帧之后**（`docs/adr/0006`：冷启动只读本地、绝不碰网络）。
   用 `Choreographer.postFrameCallback` 等首帧，再切协程发请求。
2. **任何异常都吞掉**，只记日志。健康探针失败绝不影响用户可用性。
3. **只打一次**。`@Volatile` 一次性标志 + `repeatOnLifecycle(STARTED)`，Activity 重建不重复发。

### 为什么不违反 `#50` Q6「一期网络层不被 UI 调用」

`#50` Q6 的理由是「一期没有 ViewModel，允许 Composable 直调的话将来要全改一遍」。
本类**不是 UI 逻辑**：不含状态、不含渲染，只是一个启动期一次性副作用，放在 Activity 层由
Lifecycle 驱动。将来接 ViewModel 时删掉本类即可，与 UI 层零耦合。

这一点是对 #50 Q6 的**重新解释而非推翻**，记录在此供复核。

## 2 ⚠️ R8 立刻暴露了一个真实问题（证明之前是空洞的）

接上可达引用后，第一次 `assembleRelease` **直接失败**：

```
ERROR: R8: Missing class com.google.errorprone.annotations.CanIgnoreReturnValue
  (referenced from: com.google.crypto.tink.KeysetManager
   com.google.crypto.tink.KeysetManager.add(com.google.crypto.tink.KeyTemplate) and 52 other contexts)
Missing class com.google.errorprone.annotations.CheckReturnValue
Missing class com.google.errorprone.annotations.Immutable
Missing class com.google.errorprone.annotations.RestrictedApi
```

**根因**：`tink-android:1.8.0`（`security-crypto` 的传递依赖）编译期用了 errorprone 注解，
但注解类不在运行时 classpath。这些注解**只在编译期起作用**，运行时不需要。

**处置**：`-dontwarn`（不是 `-keep`）。规则由 AGP 生成在
`app/build/outputs/mapping/release/missing_rules.txt`，已复制进 `proguard-rules.pro`。

> 这条本身就是「之前构建通过是空洞的」最好的证据 ——
> 同一份代码，只是让网络层变得可达，release 就从「通过」变成「失败」。

### 4.1 假设 #1 的验证过程（含一次反复，值得记录）

`CancelSemanticsTest` 里用 `withTimeout(1000)` 包住 `api.healthz()`，
服务端用 `setBodyDelay(3s)` 制造慢响应。若取消不传播到底层 `Call`，耗时会接近 3s。

**同一个测试先后得到两个截然不同的耗时：**

| 次 | 耗时 | 当时的判断 |
| --- | --- | --- |
| 首次（冷 JVM、冷连接） | **3.009s** | 误判为「取消没生效、假设不成立」 |
| 稳定后重复运行 | **1003ms** | 与超时值几乎一致 → **取消确实生效** |

**教训**：首次运行的 3s 是**连接建立 + 类加载/JIT 预热**造成的，不是取消语义的问题。
**基于单次耗时下结论是错的** —— 差一点就据此改了设计（退回自持 `Call`）。

**最终结论**：假设 #1 **成立**，`ApiCall` 保持「不自持 `Call`、不手写 `cancel()`」的设计。

断言写法固化在 `CancelSemanticsTest`：耗时必须在 `1000..2000ms`。
若将来退化到接近 3000ms，测试会失败并提示「需要改回自持 Call 并 cancel()」。

### 4.2 第一版取消测试「恒真」的教训

更早一版是这样写的：

```kotlin
job.cancel()
withTimeoutOrNull(2_000) { runCatching { job.await() }; true }
```

它**恒为 true** —— `job.await()` 在取消后会**立刻**抛 `CancellationException`，
而 `runCatching` 把异常吞了。测出来 5.2s，断言却通过。

**可观测的正确信号是总耗时，不是「await 有没有返回」。**
