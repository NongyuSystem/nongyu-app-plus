# 皮肤包一份契约、两条载荷通道

皮肤要能「B 端上传、用户不更新 APK 即可用」，就必须把视觉资产从 APK 发布周期里解耦出来。维护者已定「两种解耦同时做」：**色值通道**与**资源通道**两条载荷都要覆盖，且两者合在**一份皮肤包清单 + 一条下载链路**里，包内两段载荷各自可为空。这样一套版本协商、一套校验、一套缓存只写一遍，而 B 端仍可只发一个只含色值段的包。

## Status

accepted（2026-11-08，维护者在 wayfinder #23 拍板）

> **载荷范围被 ADR 0004 收窄（2026-11-08）**：维护者在 wayfinder #24 拍板 Q1=C —— **色值载荷改由数据库目录接口承载**，不再随皮肤包。因此本 ADR 的「两条载荷通道」实际只剩**资源载荷**随包；manifest 的 `colors` 段标记为 deprecated（字段保留、客户端忽略），物理删除留到 `/to-spec`。本 ADR 其余结论（一份清单 + 一条下载链路、6 项必填、三层降级、客户端判 `minAppVersion`、全局单指针、`filesDir` + 原子 rename、默认皮肤整套内置）**仍然成立**。见 `docs/adr/0004-色值通道走数据库目录接口.md`。

## 决策内容

| 项 | 结论 |
| --- | --- |
| 「两种」的所指 | **载荷通道 ×2 同时做**：色值通道（token/色值 → 色板对象）与资源通道（图标/字体等二进制）。「分隔」= 把资源本体与程序本体分开，不是 UI 分隔线控件 |
| 合拢方式 | **一份清单 + 一条下载链路**，包内两段载荷**可选、可为空**；客户端一次下载、一次校验、两路消费 |
| 清单字段 | **一次写全**（维护者选 C，与本 ADR 起草时的建议 A 不同，见下）：`packId`、`schemaVersion`、`minAppVersion`、`payload{colors, resources}`、`integrity`、`displayName`、`cover`、`author`、`description`、投放条件（地区/设备/人群）、A/B 分桶、增量包声明、回滚标记 |
| 字段必填性（本 ADR 细化） | **必填**：`packId`、`schemaVersion`、`minAppVersion`、`payload`、`integrity`、`displayName`。**结构预留、本期客户端可忽略且可为空**：`cover`、`author`、`description`、投放条件、A/B、增量包、回滚标记 |
| 降级粒度 | **三层分开**：① `schemaVersion` 主版本高于客户端支持 → 整包拒绝、回落内置默认并记日志；② 同主版本内未知字段 → 解析时忽略（`ignoreUnknownKeys = true`）；③ 单个 token / 图标缺失或无法解析 → 逐项回落内置默认，不丢整包 |
| `minAppVersion` 判定权 | **在客户端**：清单声明 versionCode 下限，客户端用 `BuildConfig.VERSION_CODE` 比对。服务端按版本过滤只能作为叠加优化，不能替代客户端判定（皮肤包会落在本地，缓存命中时服务端不在场） |
| 目录接口 | **全局单指针**：服务端只提供「当前皮肤」的 `{packId, version, url, sha256}`，所有用户同一套；B 端上传新版即换指针。不做用户可选列表（用户挑皮肤需要设置页与偏好持久化，两端都在 #20 的 Out of scope） |
| 下载与落盘 | 下到临时目录 → 校验（逐文件 sha256 + 整包签名）→ **原子 rename** 到 `filesDir/skins/{packId}/{version}/` → 原子改写**当前指针**。用 `filesDir` 而非 `cacheDir`；回滚 = 指针指回上一版；磁盘最多并存两套 |
| 内置默认皮肤的最小集 | **一整套可用的默认皮肤**：白绿全套色 token + 全套业务图标 + 默认字体。默认永不被删，离线 / 校验失败 / 未下载时必须能完整渲染首屏 |
| 不做 | Play Asset Delivery / Dynamic Feature（随 app update 更新，且大陆无 Play）；`addAssetPath` 等隐藏 API（被 non-SDK 限制，`hiddenapi-flags.csv` 实测 unsupported / blocked）；动态加载 DEX / so（触平台与政策红线）；用下载文件直接换 launcher 图标（manifest 资源，只能编译期预置 alias 间切换） |

## Considered Options（被否掉的备选）

| 备选 | 否决理由 |
| --- | --- |
| 两套独立契约、两个独立发布的包 | 两套版本协商 + 两套缓存 + 两套校验，B 端还要维护两条发布流；同一套皮肤改一次要两处对齐版本 |
| 只下发偏好标识（多套皮肤编译期内置，服务端只给 skinId） | B 端就无法「上传一套新的」，只能切换 APK 里已有的几套 —— 与维护者原话「在 b 上传皮肤」直接冲突 |
| 清单字段缩到 4 项（schemaVersion 与 minAppVersion 合并） | 格式演进与 app 兼容被混为一谈，将来判不出「格式不认识」还是「版本太低」，降级原因不可判 |
| 全有或全无的降级 | B 端每加一个 token 就让所有旧 APK 整套皮肤失效、退回白绿；且 `ignoreUnknownKeys` 默认 false 会把「加字段」变成硬失败 |
| 服务端判 `minAppVersion` | 皮肤包落在本地，缓存命中时没有服务端参与，客户端无从判断已下载的包是否仍适用 |
| 用户可选皮肤列表 | 需要设置页 + 偏好持久化，两项都在 #20 的 Out of scope；要做须先重画 destination |
| 下进 `cacheDir` | 系统清缓存会让已校验的包凭空消失，皮肤悄悄退回白绿且无告警；而完整性校验本就是应用层责任 |
| 只内置色板、图标字体留空 | 图标是导航栏骨架，远程未到时直接破版 |
| 内置多套默认皮肤 | 与 #4 已定的「本期只上白绿一套」冲突，且明显增大 APK |

## Consequences

- **Q2 选了「一次写全」，代价要如实记**：ADR 起草时建议的是最小 6 项必填，维护者选了一次写全。好处是清单格式一次成型、将来加投放条件 / A/B / 增量包不必再改 schema 版本；代价是这些字段本期就要在 B 端上传流程与入库校验里存在，而**本期并没有皮肤商店 UI**（设置页与偏好持久化在 Out of scope），等于为尚未出现的界面先付一层维护成本。本 ADR 用「必填 / 预留可空」二分把它压到最小：只有 6 项真正必填，其余结构在、值为空、客户端可忽略。
- **`schemaVersion` 与 `minAppVersion` 必须分开演进**：前者管格式能否解析，后者管 app 版本够不够；合并后再也判不出降级原因。
- **契约一旦上线就难以反悔**：B 端按此上传、客户端按此解析之后，改字段语义等于让所有已发布的包作废 —— 这正是本决策要写 ADR 的原因。
- **资源通道有 API 30 门槛**：挂进 `Resources` 的公开路径是 `ResourcesProvider` → `ResourcesLoader` → `Resources.addLoaders`（API 30+），本工程 minSdk 26，26–29 需回落到文件解码（`BitmapFactory.decodeFile` / `Typeface.createFromFile`），或本期只走文件解码。具体取舍归 #25。
- **完整性校验是应用层责任**：预签名 URL 只解决「谁能取」，不证明「是不是官方包」；下载后必须自行校验 sha256 与签名。
- **启动路径上的时机与可见性不在本 ADR**：何时检查 / 何时换肤 / 是否允许跳色 / 是否计入 TTFD，归 #28。
