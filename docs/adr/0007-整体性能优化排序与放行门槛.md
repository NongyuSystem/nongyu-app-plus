# 整体性能优化以「非代码成本优先」排序，每批改动须三件齐才放行

优化单位是整机而非组件（维护者 2026-08-11-08 方针），但「按什么顺序修」不能拍脑袋。实测给出了答案：同一份探针，debug 与 release 的冷启动中位数相差 **3.03 倍**（1164.0ms vs 384.5ms），APK 体积相差 **13.3 倍**（10.4MB vs 804KB），两组分布完全不重叠。这比任何代码级优化的潜在收益都大，所以排序必须是：**先摘掉不属于代码的成本，剩下的才按实测占比排**。

## Status

accepted（2026-11-09，维护者在 wayfinder #31 拍板）

## 决策内容

| 项 | 结论 |
| --- | --- |
| 指标主次 | **交互流畅度第一**（jank / 帧耗时）→ 冷启动 TTID/TTFD 第二 → 内存与 APK 体积第三。理由：本工程启动路径几乎为空（无 Application/ContentProvider/DI），却存在一个每秒 60 帧持续分配的常驻动画，冷启动排第一会打空 |
| 瓶颈排序 | **C→A 两步走**：先按「非代码成本」排（发布物形态 → 常驻动画 → 再进代码级），剩下的才按**实测耗时占比**排。实测已证明第一步的收益是 3.03 倍 |
| 「全组件正常」的验法 | **固定状态截帧逐像素比对 + 关键路径手工过一遍**。探针 `probe/` 已支持 `fixed_phase` 截帧开关；最低线是主题 / 导航壳 / AI 球三处固定状态截图须逐像素一致（容差待规格定） |
| 放行门槛 | **每批改动必须「改前测 → 改后测 → 全组件截帧通过」三件齐，由维护者放行**才进下一批 |
| 落地载体 | 方法写进规格；实测用 `probe/`；真机定稿沿用 #26 口径（P50 ≤ 500ms），不重复定义 |
| 硬约束 | **不得把网络拉回启动路径**（与 ADR 0006 冲突）；**不得对单个组件做单独优化**（方针） |

## Considered Options（被否掉的备选）

| 备选 | 否决理由 |
| --- | --- |
| 冷启动排第一 | 本工程启动路径几乎为空（`MainActivity.onCreate` 只有 `enableEdgeToEdge()` + `setContent{}`），官方清单里「减少初始化」类优化**无可优化对象**；第一位指标会打空 |
| 不排主次、全部按实测占比动态决定 | 每次都要重新采样；且容易在「发布物形态」这种非代码问题上反复打转，因为采样工具量不到它 |
| 只做功能回归清单 | 本工程最容易坏的不是功能而是视觉：AI 球是 9 层半透明色斑叠加、主题是一层投影，顺序或 alpha 一变肉眼看不出来 |
| 只靠手工点一遍 | 不可复核、无法回归 |
| 只在你关心的层放行、代码级小优化自行判断 | 会累积未审的视觉变化；而本图的终点是交给 `/implement` 执行的规格，规则必须写死 |
| 直接在主工程边改边测 | 启动路径几乎为空，测到的只会是噪声——这正是探针存在的理由 |

## Consequences

- **发布物形态是当前第一优先级，但尚未拍板切换**：#26 Q2 当时定「等数据再定」，数据现在有了（3.03 倍）。切换 release 需要 R8 keep 规则、签名配置、`AGENTS.md` 打包流程重写，成本不小；本 ADR **只定了排序，没有替你决定切换**。
- **「交互流畅度第一」意味着必须回真机**：蓝叠 `enable_vsync=0` + 60fps 上限，给不出可信帧率。这条与 #26 合并成一笔债。
- **截帧比对的容差未定**：逐像素完全一致在抗锯齿下往往做不到，规格里需要一个可接受的阈值。
- **探针只测了总启动时间**，三类负载（120 项首帧组合 / 7 层羽化 / 12 层嵌套）各自的占比未做 Perfetto 归属。「按实测占比排序」这一步在代码级落地前，需要先补这个归属。
- **每批三件齐 + 人工放行**会让节奏变慢，这是刻意的：代价换的是「不会偷偷把某个组件弄坏」。
